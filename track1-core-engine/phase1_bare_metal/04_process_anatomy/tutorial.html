TRACK 1 · PHASE 1 · MODULE 04

process_anatomy

Proves: a process is a kernel-tracked bundle of identity, a security context, a handle table, and N threads — every piece independently, live-queryable, both about yourself and (with the right handle) about another process entirely.

00Prerequisites

the Process Control Block process vs. thread handles as scoped access

01The Big Analogy

"The running program" feels like one solid thing, the way "a company" feels like one solid thing from the outside. But a company is actually a filing cabinet at the county clerk's office: an identity number, a registered legal status, a list of employees (threads) currently doing work, a list of assets and accounts it's allowed to touch (handles), and a record of who it's legally allowed to act as (its security context). None of that is visible by looking at the storefront. It's all sitting in a government record, and — crucially — a sufficiently authorized outside party (an auditor with the right paperwork) can pull that exact same filing-cabinet record for a company that isn't their own. That's what this module does to a process.

02What Happens, Step by Step

  1. process_anatomy.py asks the OS for its own "pseudo-handle" (GetCurrentProcess()) — a handle that always just means "me," requiring no permission check.
  2. It queries memory usage, open handle count, thread count, and the security token's integrity level — four genuinely different kernel subsystems, each answering a different piece of "what is this process."
  3. inspect_child_process.py spawns a real second Python process.
  4. Rather than a free pseudo-handle, it must call OpenProcess(), explicitly naming which access rights it wants — the kernel checks whether the calling process is allowed those rights against that target before handing back a real handle.
  5. With that handle in hand, the exact same query functions run again — this time reading a genuinely different process's kernel state from the outside.

04The Code, Explained

access = win32con.PROCESS_QUERY_INFORMATION | win32con.PROCESS_VM_READ
handle = win32api.OpenProcess(access, False, child.pid)

mem = win32process.GetProcessMemoryInfo(handle)
threads = count_threads(child.pid)
handles = handle_count(handle)
level_name, level_rid = integrity_level(handle)

Notice this is the identical set of function calls process_anatomy.py made about itself — the only thing that changed is where handle came from. A bare PID (child.pid) is just an integer; it grants nothing. OpenProcess() is the actual gate — the kernel decides, based on the calling process's own security context and the requested rights, whether to hand back a usable handle at all.

If OpenProcess in inspect_child_process.py raises an access-denied error: check that no antivirus/EDR policy on your machine is specifically restricting inter-process handle grants for Python processes (some hardened endpoint configurations do this). This module's expected result requires nothing more than a normal, non-elevated user session — no Administrator rights needed for these specific access rights against a same-user child process.

07Brain Exercise

Two processes both show integrity level "Medium." Does that tell you they're allowed to do the same things as each other? Think about what else determines a process's actual permissions before revealing the answer.
No. Integrity level is one input the kernel uses when deciding what a process can touch — mainly, it enforces that lower-integrity processes can't write to or manipulate higher-integrity ones. But the full picture of what a process can do also depends on its token's group memberships, its specific granted/denied privileges (like SeDebugPrivilege), and any restricting SIDs or AppContainer capabilities attached to it. Two "Medium" processes can still have meaningfully different real-world permissions. This distinction matters directly for Module 9, where a sandboxed renderer process is deliberately given a more restricted token than a plain integrity-level comparison alone would suggest.

08There Are No Dumb Questions

Why does the child process show fewer open handles than the parent (89 vs. 173)?
Every process accumulates handles as it initializes — loaded DLLs, heap sections, synchronization objects created by the runtime, etc. Our parent process (running this whole test harness) had simply done more by the time we measured it than the freshly spawned, nearly idle child had. Neither number is "correct" in isolation — they reflect each process's own history so far.
Could I get a handle to ANY process on the system this way?
Only if the kernel's access check allows it — which depends on your process's own privileges and the target's integrity level and owner. Trying to OpenProcess a higher-integrity or different-user process with the same code would very plausibly fail with access denied. This module deliberately targets a same-user child to keep the demonstration reliable without requiring elevation.
Is "integrity level" the same thing as "is this process an Administrator"?
No — related, but not the same axis. Integrity level (Low/Medium/High/System) is about what a process can be written to or manipulated by from other processes. Whether a token has Administrator group membership is a separate property governing what privileged operations the process can request from the kernel. A process can be "Medium" integrity and still hold Administrator group membership (this is exactly what UAC's split-token behavior manages).
Why does count_threads need to scan every thread on the whole system?
Because that's genuinely how the Toolhelp32 snapshot API works — see DECISIONS.md. There's no "give me thread count for PID X" shortcut in this API family; you snapshot everything and filter client-side.
