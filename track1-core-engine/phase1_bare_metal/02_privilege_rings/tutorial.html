TRACK 1 · PHASE 1 · MODULE 02

privilege_rings

Proves: user-mode (Ring 3) code physically cannot execute a privileged CPU instruction — the CPU itself refuses, before the instruction has any effect, with no OS intervention required.

00Prerequisites

Ring 0 vs Ring 3 hardware-enforced, not OS-enforced the trap into Ring 0

01The Big Analogy

Picture a car with a physical governor bolted to the engine that hard-caps top speed at 65 mph — not a dashboard warning light, not a software speed limiter you could argue with, an actual mechanical stop that makes the engine physically incapable of turning faster than that. You can floor the pedal all you want; the request never even reaches "the engine ignoring you," because the fuel simply doesn't get there past that RPM. That's the difference between a rule and a hardware boundary. A privileged instruction executed at Ring 3 isn't "denied by policy" — the CPU's own decode logic checks the current privilege level before the instruction can do anything, and refuses at that exact moment, every time, unconditionally.

02What Happens, Step by Step

  1. Python asks Windows for a page of memory and marks it PAGE_EXECUTE_READWRITE — the OS grants it, because allocating executable memory is itself an unprivileged, ordinary request any Ring 3 process can make.
  2. We hand-write raw machine code bytes into that page — e.g. 0xFA, the exact byte encoding of the CLI instruction.
  3. We call into that page as if it were a normal function.
  4. The CPU begins executing our bytes at Ring 3 (nothing has changed our privilege level — we're still ordinary user code).
  5. The CPU's instruction decoder reaches CLI, checks the Current Privilege Level register, sees CPL=3, and raises a #GP (General Protection) fault — before the interrupt flag is touched.
  6. Windows' kernel-level fault handler catches this CPU exception and translates it into STATUS_PRIVILEGED_INSTRUCTION, delivered to our process as a structured exception.
  7. CPython's ctypes module — which wraps every foreign call in a Windows SEH frame specifically to catch exactly this kind of fault — converts it into an ordinary Python OSError we can catch.

03What We Actually Captured

instruction                                                   result
------------------------------------------------------------------------------------------
NOP  (no-op -- Ring 3 legal)                                  OK
RDTSC (read timestamp counter -- Ring 3 legal by default)     OK
CLI  (clear interrupt flag -- PRIVILEGED, Ring 0 only)        FAULT   <- exception: privileged instruction
HLT  (halt the CPU -- PRIVILEGED, Ring 0 only)                FAULT   <- exception: privileged instruction
Real captured output. Two ordinary instructions ran cleanly. Two privileged instructions faulted every time, with the exact same "privileged instruction" message ctypes produces for STATUS_PRIVILEGED_INSTRUCTION.

04The Code, Explained

INSTRUCTIONS = {
    "NOP  (no-op -- Ring 3 legal)": bytes([0x90, 0xC3]),
    "CLI  (clear interrupt flag -- PRIVILEGED, Ring 0 only)": bytes([0xFA, 0xC3]),
    ...
}

def run_code(code: bytes):
    addr = kernel32.VirtualAlloc(None, len(code), MEM_COMMIT | MEM_RESERVE,
                                   PAGE_EXECUTE_READWRITE)
    ctypes.memmove(addr, code, len(code))
    func = ctypes.CFUNCTYPE(None)(addr)
    try:
        func()
        return "OK", None
    except OSError as e:
        return "FAULT", str(e)

Every byte in INSTRUCTIONS is real x86-64 machine code — 0xFA isn't a stand-in or a symbol, it's the literal encoding the CPU decodes as CLI. We write it into genuinely executable memory and jump into it directly. There's no simulation layer: this is your actual CPU deciding, in real time, whether to allow or refuse each instruction based on the privilege level it's currently running our code at.

07Brain Exercise

You're told a piece of malware achieved "arbitrary code execution" inside a browser's renderer process. Does that alone mean the malware can execute privileged instructions like CLI or HLT? Reason it through before revealing the answer.
No. "Arbitrary code execution" means the attacker can make the process run instructions of their choosing — but that process is still, unavoidably, running at whatever CPU privilege level it started at. A browser renderer process runs at Ring 3 like any other user-mode process. The malware's injected code inherits that same Ring 3 restriction — it can execute CLI all it wants and the CPU will fault it exactly like our demo did. Getting from "arbitrary Ring 3 code execution" to "Ring 0 access" requires a genuinely separate exploit: either a bug in a system call's kernel-side handling, or a bug in a device driver running in kernel mode, or similar — it is never a free upgrade that comes bundled with a renderer bug. This exact gap is why sandboxing (Track 1, Phase 3) is valuable even against attackers who already have full code execution inside the sandbox.

08There Are No Dumb Questions

Why doesn't the process just crash silently instead of raising a Python exception?
Because ctypes on Windows specifically wraps foreign-function calls in SEH (Structured Exception Handling) so that low-level hardware faults become ordinary, catchable Python exceptions instead of tearing down the interpreter. This is a CPython/ctypes design choice for robustness, verified directly in this module's Run It step — not a universal property of "running machine code."
If I run this as Administrator, will CLI succeed?
No. Administrator/root is a kernel-side authorization concept — it changes what the kernel will permit when you ask it to do something via a syscall. It has no effect on which CPU ring your own code's instructions execute at. This exact confusion is called out explicitly in Prerequisite 2.
Could a kernel driver bug let user-mode code run CLI directly?
Not directly — but a vulnerable driver (which itself runs at Ring 0) could be tricked into executing privileged operations on the attacker's behalf. That's a real, well-known privilege-escalation pattern, and it's exactly why "vulnerable signed driver" exploitation is a known attack category — but note it still routes through a Ring 0 component doing the privileged work, never through Ring 3 code executing CLI directly.
Why RDTSC and not something else as the "boring" control case?
RDTSC (read timestamp counter) is a good contrast specifically because it sounds like it should be privileged — it reads low-level CPU state — but by default it's permitted at Ring 3 (the CR4.TSD bit can restrict it, but that's not the default). It's a useful reminder that "sounds low-level" and "is privileged" are not the same test; only the ISA's actual privilege designation matters.
