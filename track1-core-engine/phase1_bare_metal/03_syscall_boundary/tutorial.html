TRACK 1 · PHASE 1 · MODULE 03

syscall_boundary

Proves: every "browser action" that touches the outside world (open a file, open a socket) is a request crossing one shared kernel boundary — by bypassing the friendly Win32 API entirely and reaching the same file, and the same refusal, directly.

00Prerequisites

the syscall boundary as a chokepoint Win32 API vs. ntdll vs. the kernel the trap into Ring 0

01The Big Analogy

A government office has a fancy public-facing service counter with friendly forms in plain language ("Request a copy of your birth certificate"). Behind that counter, every single form gets translated into one internal case-file format and handed through one interior door to the actual records clerk — the only person with the keys to the archive. You could, in principle, walk around the public counter and knock directly on the interior door, speaking the clerk's internal case-file jargon yourself. You'd get the identical record, because there was only ever one archive and one clerk. The public counter was never a separate authority — it was a translation layer in front of the one door that actually matters.

02What Happens, Step by Step

  1. Python's open() writes a file — internally, this calls kernel32's CreateFileW (the "public counter").
  2. nt_native_layer.py then reads that same file back, but skips kernel32 entirely: it calls ntdll!NtCreateFile and ntdll!NtReadFile directly (the "interior door").
  3. Both paths return the identical bytes — because both paths were always terminating at the same kernel file object underneath.
  4. same_kernel_decision.py then asks both layers to open a file that doesn't exist.
  5. The Win32 layer reports failure as GetLastError() == 2 (ERROR_FILE_NOT_FOUND). The NT layer reports the exact same refusal as NTSTATUS == 0xC0000034 (STATUS_OBJECT_NAME_NOT_FOUND).
  6. These two codes aren't a coincidence — Windows' own RtlNtStatusToDosError() function is what translates the NT status into the Win32 error code internally. The Win32 number is derived from the NT number, proving there's one decision, made once, reported in two vocabularies.

04The Code, Explained

status = ntdll.NtCreateFile(
    ctypes.byref(handle),
    GENERIC_READ | SYNCHRONIZE,
    ctypes.byref(attrs),
    ctypes.byref(open_iosb),
    None, 0,
    FILE_SHARE_READ | FILE_SHARE_WRITE,
    FILE_OPEN,
    FILE_SYNCHRONOUS_IO_NONALERT | FILE_NON_DIRECTORY_FILE,
    None, 0,
)

This is a real call into ntdll.dll — the exact same DLL that kernel32's CreateFileW itself calls into internally. Nothing here is faked or wrapped in a compatibility shim; the structs (ntdll_structs.py) are hand-declared to match the NT native API's real, if semi-private, binary contract (see DECISIONS.md). When this call succeeds, you are one function call away from the kernel — closer to the syscall boundary than any Win32 application code normally gets.

While building this exact module, an early version of same_kernel_decision.py printed succeeded? True for the "open a missing file" test on both layers — which looked like the whole experiment was broken. The real cause: Win32's OPEN_EXISTING (value 3) and the NT native FILE_OPEN (value 1) are different numbers for a similarly-named idea, and the first draft accidentally passed the NT constant into the Win32 call — which Win32 reads as CREATE_NEW, so it quietly created the "missing" file instead of failing to find it. If you ever see a stray file appear when running this script, that's this exact class of bug, not a broken environment. Full account in DECISIONS.md.

07Brain Exercise

If a security product hooks (intercepts) kernel32's CreateFileW to monitor file access, would this module's nt_native_layer.py approach be visible to that hook? Reason about where the hook sits before revealing the answer.
No — and this is precisely why it matters that there's a layer below the Win32 API. A hook placed on kernel32's CreateFileW only sees calls that actually go through that specific function. Code that calls ntdll!NtCreateFile directly, as this module does, never touches kernel32's CreateFileW at all — the hook is simply never reached. This is exactly why real security tooling that wants complete visibility places its hooks at the ntdll layer (or lower, at the kernel itself via a driver/ETW), not at the Win32 layer — the Win32 layer is demonstrably not the true chokepoint, even though it's the one most application code happens to use. The real, unavoidable chokepoint is the syscall instruction itself, which is why kernel-level or ETW-based monitoring is considered more complete than userland API hooking.

08There Are No Dumb Questions

Is calling ntdll functions directly "hacking" the OS?
No — it's an unusual but legitimate way to call functions that are exported and callable like any other DLL function; Windows doesn't prevent it. It's "semi-private" in the sense that Microsoft doesn't provide official documentation or support guarantees for these specific functions changing between Windows versions — not in the sense that calling them is prohibited or exploits a flaw.
Why does the Win32 layer even exist if it's "just" a wrapper?
Convenience, stability, and compatibility — kernel32 provides a documented, supported, relatively stable API surface that application developers can rely on across Windows versions, while the NT native layer underneath has changed internal details over the years. The wrapper is genuinely useful; this module's point is only that it isn't the security boundary some people assume it is.
Does this mean the Same-Origin Policy in a browser is enforced "at the syscall level" too?
No, and this is an important distinction to hold onto going into Track 2: SOP is a browser-application-level policy, enforced by browser code before it ever gets near a syscall — the OS has no concept of "origin" at all. The syscall boundary is what OS-level sandboxing (Modules 9–11) uses; SOP and friends (Module 17 onward) are enforced entirely inside the browser's own code, one layer up.
What actually happened with the "missing file got created" bug?
Covered in detail in DECISIONS.md — briefly: two different Win32 and NT enums share the numeric value 1 for different meanings (CREATE_NEW vs. FILE_OPEN), and an early draft mixed them up. It's kept in the docs as a real, concrete illustration of "these are two different vocabularies," which is this module's whole point.
