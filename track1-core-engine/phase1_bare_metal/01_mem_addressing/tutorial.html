TRACK 1 · PHASE 1 · MODULE 01

mem_addressing

Proves: a virtual address is a per-process, per-run illusion — never a fixed physical location — by running the identical program twice and diffing what it sees.

00Prerequisites

virtual memory · address space pages & page tables ASLR reading hex addresses

01The Big Analogy

You check into a hotel and the front desk says "you're in Room 214." You go up, unlock 214, drop your bags. The next week you stay at the same hotel chain, same city, and you're again told "Room 214." Naturally you'd assume you're back in your old room — except this time it's a different building entirely, the hotel just reuses room numbers per booking. Nothing physical connects this week's "214" to last week's "214." The number is a label the front desk hands out fresh, per stay, that only means something in combination with which stay you're currently on. Your program's memory addresses work exactly like that room number: meaningful only within this one run, re-issued from scratch the next time.

02What Happens, Step by Step

  1. You run addr_dump.py. Python's interpreter starts as a brand-new OS process and asks Windows for a fresh virtual address space — the OS has not yet decided where anything will live.
  2. The OS loader picks base addresses for the executable, the loaded DLLs, the heap, and the stack — partly randomized by ASLR — and builds this process's private page tables mapping virtual pages to physical RAM frames.
  3. Your script creates a few objects (local_int, local_list, a function). CPython's memory allocator carves space for them out of the process's heap region.
  4. id(obj) returns CPython's internal notion of identity, which — as a documented CPython implementation detail — is the object's virtual address in this process.
  5. For each address, the script calls the real Win32 VirtualQuery function, which asks the kernel to look up that address in this process's own page tables and report back the page's base, size, and permission bits.
  6. prove_aslr_illusion.py repeats all of the above twice, as two independent processes, and diffs the results.

04The Code, Explained

Here's the part of addr_dump.py doing the real work:

kernel32 = ctypes.windll.kernel32
kernel32.VirtualQuery.argtypes = [
    ctypes.c_void_p,
    ctypes.POINTER(MEMORY_BASIC_INFORMATION),
    ctypes.c_size_t,
]
kernel32.VirtualQuery.restype = ctypes.c_size_t

def query_page(address: int) -> MEMORY_BASIC_INFORMATION:
    mbi = MEMORY_BASIC_INFORMATION()
    written = kernel32.VirtualQuery(
        ctypes.c_void_p(address), ctypes.byref(mbi), ctypes.sizeof(mbi)
    )
    ...
    return mbi

This isn't a simulation of what an OS memory query would look like — kernel32.VirtualQuery is the actual Windows API function, called through ctypes with no emulation layer in between. The MEMORY_BASIC_INFORMATION struct is hand-declared to match Windows' real ABI byte-for-byte (see DECISIONS.md for exactly why every field and every padding byte is there). When this function call succeeds, you are looking at the live, actual state of your process's own page tables — the same data structure the CPU's MMU consults on every single memory access your program makes.

06Run It

cd track1-core-engine/phase1_bare_metal/01_mem_addressing
python addr_dump.py
python prove_aslr_illusion.py

Expected: addr_dump.py prints four objects' addresses and page info. prove_aslr_illusion.py prints a table where every "identical?" column says no, followed by a CONFIRMED message.

If prove_aslr_illusion.py ever prints an UNEXPECTED result with a repeated address: this is not automatically a broken demo. Some hardened/managed environments disable ASLR system-wide, and there's a real (tiny) chance of coincidental collision in a large address space. Check DECISIONS.md before assuming something's wrong — and if you genuinely have ASLR disabled, that's itself worth knowing about your environment.

07Brain Exercise

If two DIFFERENT processes, running the identical script at the identical moment, both printed the exact same numeric address — say, both print 0x1F6330144B0 for their "fresh int" — would that mean one process could read the other's data at that address? Think it through before revealing the answer.
No. A numeric coincidence in the address alone proves nothing, because that number only has meaning relative to a specific process's page tables. Process A's page tables might map 0x1F6330144B0 to physical frame X; Process B's completely separate page tables might map that same virtual number to physical frame Y, or to nothing at all (an unmapped page, causing a fault). There is no way to "reach across" using the number itself — you would need an actual handle into the other process's address space (which the OS tightly controls; see Module 4 and Module 9) to have any hope of touching its memory. This is exactly why matching addresses is not a security concern by itself, and why isolation depends on separate page tables, not on addresses being unpredictable.

08There Are No Dumb Questions

Isn't id() just a Python thing, unrelated to "real" memory?
In CPython specifically, no — it's documented to return the object's actual memory address. This is a CPython implementation detail, not a language-spec guarantee, which is exactly why DECISIONS.md flags it as an external contract we're relying on rather than something inherent to Python as a language.
Why does the region size (901120 bytes) look so oddly specific?
That's CPython's own heap arena allocator (pymalloc) requesting memory from the OS in its own chunk sizes — that number is a property of CPython's allocator, not of Windows or the CPU. Different Python versions or a different allocator would show different, but equally "real," numbers.
Could I run the equivalent of this on Linux?
Yes, conceptually — you'd read /proc/self/maps instead of calling VirtualQuery, since that's the Linux-native way to query your own process's page mappings. This course's primary track builds the Windows version, per the tools decision in the root ROADMAP; the Linux equivalent is a fair exercise but isn't built here.
Doesn't ASLR mean my program is "safe" from memory bugs?
No — and this is exactly the trap Module 12 exists to walk you into. ASLR only raises the cost of guessing an address; a single information leak (a bug that reveals even one real address) can collapse the randomization instantly, because once you know one address you often know the offsets to everything else.
Why does prove_aslr_illusion.py parse text with regex instead of using a cleaner data format?
Deliberate tradeoff, explained in DECISIONS.md: addr_dump.py's output is optimized for a human reading it directly first, not for a downstream parser.

09What's Next

You've now proven that addresses are per-run illusions — but you haven't yet proven the boundary that enforces that illusion. Module 2 goes one layer down: it proves that your code, running at Ring 3, physically cannot execute a privileged CPU instruction without the hardware itself refusing — the mechanism that makes "user mode can't touch kernel territory" a hardware fact rather than an OS-enforced courtesy.
