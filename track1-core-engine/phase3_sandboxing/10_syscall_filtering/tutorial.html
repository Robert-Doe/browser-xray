TRACK 1 · PHASE 3 · MODULE 10

syscall_filtering

Proves: a process can be blocked from an entire CATEGORY of operation — spawning any new process at all — enforced by the kernel itself, regardless of what ordinary, unprivileged code inside that process tries.

00Prerequisites

Module 9: least_privilege_tokens the syscall boundary as a chokepoint

01The Big Analogy

Module 9's badge could open some doors and not others, based on printed clearance — but the badge holder could still, in principle, try any door. This module is different: imagine a turnstile with a hard mechanical counter bolted to it, pre-set to "admit exactly one person, ever, for this event." It doesn't matter who the eleventh person is, what badge they're holding, or how politely they ask — the turnstile's arm is physically locked once the counter hits its limit. No check of identity happens at all for the eleventh person, because the mechanism refuses before identity is even relevant.

02What Happens, Step by Step

  1. The orchestrator creates a Windows Job Object — a kernel object that can hold a group of processes under a shared set of limits.
  2. It sets that job's ActiveProcessLimit to 1.
  3. It spawns probe_spawn_child.py suspended, assigns it to the job (filling the job's one allowed slot), then resumes it.
  4. The probe — ordinary code, no awareness of any restriction — calls subprocess.run(), the same call any Python script would use to spawn a helper process.
  5. Because any child it spawns would automatically join its parent's job (Windows' default behavior) and the job is already at its limit, the OS refuses to create the new process at all.
  6. The refusal surfaces as an ordinary OSError, not a crash — the probe simply cannot make this particular syscall succeed.

03What We Actually Captured

=== Part A: probe_spawn_child.py running WITHOUT any Job Object restriction ===
[orchestrator] spawned unrestricted probe, PID 39260
spawn attempt SUCCEEDED: child said 'a new process ran'

=== Part B: probe_spawn_child.py running INSIDE a Job Object (ActiveProcessLimit=1) ===
[orchestrator] created a Job Object with ActiveProcessLimit=1
[orchestrator] assigned PID 24744 to the job -- it now occupies the job's ONE permitted process slot
spawn attempt BLOCKED by the OS: [WinError 1816] Not enough quota is available to process this command
Real, captured output. Identical code, identical interpreter — the only difference between success and refusal was the Job Object.

04The Code, Explained

info["BasicLimitInformation"]["LimitFlags"] = win32job.JOB_OBJECT_LIMIT_ACTIVE_PROCESS
info["BasicLimitInformation"]["ActiveProcessLimit"] = 1
win32job.SetInformationJobObject(job, win32job.JobObjectExtendedLimitInformation, info)
...
win32job.AssignProcessToJobObject(job, h_process)

Notice what probe_spawn_child.py itself contains: zero awareness of Job Objects. It just calls subprocess.run(). That's exactly the point — a kernel-enforced restriction doesn't require the restricted code's cooperation, unlike an application-level check that a bug (or an attacker) could find a way around.

05Limits / What You Cannot Do Yet

CAN'T DO YET

  • Put two different origins in two different, differently restricted processes on purpose (Module 11)
  • Block a specific FILE or NETWORK operation this same way (Job Objects mainly restrict resource counts/UI, not arbitrary syscalls — real fine-grained syscall filtering on Windows needs different, more specialized mechanisms than this module built)

CAN DO NOW

  • Contain a process's ability to spawn further processes, unconditionally, at the OS level
  • Explain why kernel-enforced restrictions are categorically stronger than restrictions the sandboxed code could observe and route around
  • Combine this with Module 9's least-privilege token for a two-layer restriction (this module's demo doesn't combine them, but nothing stops you from doing so)

python run_job_object_demo.py
If Part B's spawn attempt UNEXPECTEDLY succeeds: double-check you're running the exact provided script — a common mistake when experimenting is assigning the process to the job AFTER resuming it, opening a timing window where it could spawn its child before the restriction takes effect. The provided script's CREATE_SUSPENDED ordering exists specifically to prevent that race; removing it can reintroduce the race.

07Brain Exercise

This module's DECISIONS.md describes an earlier attempt — Win32k System Call Disable — that looked like it succeeded (every API call returned success) but, on direct verification, hadn't actually taken effect. Why is "the API returned success" not sufficient evidence that a security mitigation is active? Think about what you'd need to check instead, before revealing the answer.
Because a success return value only tells you the function call completed without an immediately-detected error — it says nothing about whether the requested *effect* actually took hold, especially for APIs (like process mitigation policies) that configure something to be enforced later, at a different moment, by a different code path. The only way to know a mitigation genuinely works is to test the actual enforcement directly: attempt the exact operation the mitigation claims to block, and observe whether it's actually refused — which is precisely why this module's own build process pivoted away from a mechanism that "returned success" everywhere but demonstrably didn't work when tested end-to-end, rather than writing tutorial content based on the API's return codes alone. This is a genuinely transferable security-research habit: distrust "no error was returned" as proof of anything security-relevant; test the actual boundary.

08There Are No Dumb Questions

Why does the failure happen inside CreateProcess itself, rather than at a separate "join the job" step?
Because Windows automatically adds a newly created child process to its parent's Job Object by default (unless the job explicitly allows "breakaway"). Since the new process would be joining a job already at its limit, the creation itself is refused — there's no separate step where it briefly exists outside the job first.
Could the restricted process detect it's in a job and behave differently?
Yes, actually — IsProcessInJob() is a real, callable Win32 API a process could use to check. But detecting the restriction and being able to remove or bypass it are very different things; nothing about knowing you're restricted lets ordinary code escape a kernel-enforced Job Object limit.
Is this exactly what real Chromium does?
The same underlying primitive (Job Objects, including active-process-count-style limits) is real and used by Chromium's Windows sandbox, alongside several other layered restrictions (integrity levels from Module 9, restricted tokens, and more) — real production sandboxing typically combines many such mechanisms rather than relying on just one, which is exactly why this course builds them as separate, composable modules instead of one monolithic "sandbox" module.
What's the difference between this and Module 9's restriction?
Module 9 restricted access to a specific, identified resource (one file) based on a comparison between the process's credentials and that resource's label. This module restricts an entire category of operation (creating any process) with no per-resource check involved at all — the refusal happens before the kernel even considers what the new process would be.
