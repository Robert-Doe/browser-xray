TRACK 1 · PHASE 3 · MODULE 09

least_privilege_tokens

Proves: a process's OS-level rights can be reduced below its parent's, purely via the security token it's launched with — same Windows user account, same file, same code, genuinely different outcome.

00Prerequisites

Module 4: process_anatomy (integrity levels) handles carry access rights

01The Big Analogy

A hospital issues every staff member the same photo ID badge format — but a badge can be printed with different clearance stripes on it. A surgeon's badge and a visitor-escort's badge might belong to employees with the identical HR record, identical login, identical name — but the badge itself carries a printed clearance level the door readers check. Hand that same person a "visitor" badge instead of their usual one, and the same person, unchanged, suddenly can't open the same doors they could a moment ago. Nothing about who they are changed. What changed was the badge.

02What Happens, Step by Step

  1. The parent process duplicates its own security token — not anyone else's — which Windows always permits without special privilege.
  2. It sets the duplicate's integrity level field to "Low" — also always permitted, since lowering integrity never requires elevated rights (only raising it does).
  3. It calls CreateProcessAsUser with that lowered token — normally a privileged operation, except Windows exempts this specific case: spawning with a duplicate of your own token.
  4. The resulting child process runs as the identical Windows user account, but every access check the kernel performs for it now also considers that Low integrity label.
  5. The child attempts to read, then (in a separate run) write, the identical file the parent created.

03What We Actually Captured

=== Attempt 1: Low-integrity child, READ ===
READ OK: 'data owned by the parent (Medium-integrity) process'

=== Attempt 2: Low-integrity child, WRITE ===
WRITE FAILED: PermissionError: [Errno 13] Permission denied: '...\parent_owned_file.txt'

=== Attempt 3 (control): Medium-integrity child, WRITE ===
WRITE OK
Real, captured output. Same file, same user account, same code — only the token's integrity level changed between attempts 2 and 3.

04The Code, Explained

duplicate = win32security.DuplicateTokenEx(
    original_token, win32security.SecurityImpersonation,
    win32con.TOKEN_ALL_ACCESS, win32security.TokenPrimary, None,
)
sid = win32security.ConvertStringSidToSid(INTEGRITY_SIDS["low"])
win32security.SetTokenInformation(
    duplicate, ntsecuritycon.TokenIntegrityLevel, (sid, SE_GROUP_INTEGRITY)
)

This is the entire mechanism, and notice what it does not involve: no new user account, no password, no service, no administrator elevation. It's a copy of a token this process already legitimately holds, with one field set to a lower value. That's the whole primitive real sandboxes are built from.

05Limits / What You Cannot Do Yet

CAN'T DO YET

  • Block specific syscalls outright, regardless of integrity level (Module 10)
  • Explain why READ succeeded here — that gap is exactly what motivates combining integrity levels with OTHER restrictions in a real sandbox (Module 10's job)

CAN DO NOW

  • Spawn a genuinely less-privileged child process without needing elevation or a separate account
  • Correctly distinguish "no write up" from "no access at all" — a frequently confused pair
  • Read a permission failure and know precisely which mechanism (DACL vs. integrity label) is responsible

07Brain Exercise

Attempt 1 (Low-integrity READ) succeeded. Does that mean a Low-integrity renderer process could read your browser's saved passwords file, if it somehow knew the path? Think about what would ACTUALLY need to be true for that, before revealing the answer.
Not by integrity level alone — but this is exactly the gap real browser sandboxes have to close with something beyond what this module built. If a sensitive file only relies on the DEFAULT "no write up" MIC policy, a Low-integrity process genuinely CAN still read it, exactly like Attempt 1 showed. Real hardened systems close this gap in (at least) one of two ways: explicitly marking specific sensitive files/objects with a stricter "no read up" policy via their mandatory label (not the default), or — the approach Module 10 introduces — restricting which syscalls/APIs the process can even attempt in the first place, regardless of what the target's ACL or integrity label says. This module deliberately surfaced the read-succeeds gap rather than hiding it, because assuming "low integrity = can't read anything" is a real, dangerous misconception worth correcting directly.

08There Are No Dumb Questions

Why doesn't creating this low-integrity child need Administrator rights?
Because you're only ever narrowing your own already-held rights, never claiming someone else's. Windows' privilege checks exist to stop you from acting as someone more privileged than you — they were never designed to stop you from acting as less. See DECISIONS.md for the exact mechanism.
Is "integrity level" the only thing separating a sandboxed renderer from a normal process in real Chromium?
No — integrity level is one layer among several (also restricted tokens with specific SIDs removed/denied, job objects, and on newer designs, more granular capability-based restrictions). This module deliberately isolates just the integrity-level piece so it can be understood on its own before Module 10 adds syscall-level filtering on top.
What would happen if I tried to RAISE a token's integrity instead of lowering it?
SetTokenInformation would fail — raising requires SeRelabelPrivilege, which an ordinary user token does not hold by default. This isn't a bug in the module; it's the exact asymmetry (easy to lower, hard to raise) that makes least-privilege delegation safe to do without a broker process.
Why is the write failure a plain PermissionError rather than something more specific mentioning "integrity"?
Python's open() surfaces the underlying Win32 access-denied error as a generic PermissionError — the OS doesn't distinguish "denied by DACL" from "denied by mandatory integrity policy" in the error Python receives at this level. Confirming which mechanism caused a specific denial (as opposed to just knowing something was denied) generally requires lower-level tooling than a plain Python file open.

09What's Next

You've reduced what a process can touch. Module 10 reduces what a process can even attempt — blocking specific syscalls outright at the OS level, regardless of what any file's permissions or integrity label say, closing exactly the kind of gap this module's Brain Exercise surfaced.
