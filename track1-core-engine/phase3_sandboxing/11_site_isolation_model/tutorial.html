site_isolation_model

Proves the precise, easy-to-oversimplify claim Site Isolation actually depends on: process separation alone does NOT stop a deliberate cross-process memory read — only process separation combined with a real trust difference does.

00Prerequisites

Module 5: process_creation Module 9: least_privilege_tokens the origin tuple

01The Big Analogy

Two hotel rooms, different keys, different doors — clearly separated. But if the same locksmith who cut your key can also cut a copy for the room next door, "different rooms" was never actually keeping anyone out on its own. Real security came from the locksmith refusing to cut that second key for someone with lower standing — not from the rooms simply being different rooms. Module 5 proved the rooms are different. This module asks the sharper question: is that alone enough to keep one guest out of another's room? The honest answer, demonstrated directly, is no — you also need the locksmith (the OS's access control) to actually refuse.

02What Happens, Step by Step

  1. A "victim" process (standing in for origin B's renderer) pins a known address and writes a secret into it.
  2. Part A: an unrestricted "attacker" process (origin A's renderer, no sandboxing applied) calls OpenProcess on the victim's PID, then ReadProcessMemory on the known address.
  3. It succeeds — the OS had no reason to refuse a same-user, same-privilege request.
  4. Part B: the identical attack, except the attacker now runs under a Module-9-style LOW-integrity token, while the victim stays at the OS default (Medium).
  5. OpenProcess itself is refused — Windows' Mandatory Integrity Control enforces "no read up" specifically for process and thread objects.

03What We Actually Captured

=== Part A: unrestricted, same-integrity cross-process read ===
[victim: origin B renderer] PID 23712 holding a secret at 0x300000000000
[attacker: origin A renderer] OpenProcess(PID 23712) -> handle=192, GetLastError=0
[attacker] ReadProcessMemory SUCCEEDED: b'ORIGIN_B_SESSION_TOKEN_SECRET\x00...'

=== Part B: attacker forced to LOW integrity, victim stays Medium ===
[victim: origin B renderer] PID 32988 holding a secret at 0x300000000000
[attacker: origin A renderer] OpenProcess(PID 32988) -> handle=0, GetLastError=5
[attacker] cannot proceed -- no handle means no ReadProcessMemory is possible.
Real, captured output. Same secret, same known address, same attack code — the only variable that changed the outcome was whether a genuine trust difference existed between the two processes.

04The Code, Explained

handle = kernel32.OpenProcess(
    PROCESS_VM_READ | PROCESS_QUERY_INFORMATION, False, target_pid
)
...
ok = kernel32.ReadProcessMemory(handle, ctypes.c_void_p(PINNED_ADDRESS), buffer, 64, ...)

Every line here is an ordinary, fully documented Win32 call — the same two functions a legitimate debugger uses. Nothing about them is inherently an "exploit." What determines whether this succeeds is entirely the kernel's own access-control decision at the moment of OpenProcess — which is exactly why Part A and Part B differ only in that one line's return value.

07Brain Exercise

Real Chromium didn't ship Site Isolation as a day-one feature — it was added years after the original multi-process architecture (Module 8's shape), and specifically strengthened again after Spectre (2018). Given what this module just proved, why would "put origins in different processes" alone have felt sufficient for years, before someone needed to add more? Think about what threat model changed, before revealing the answer.
Because for a long time, the primary threat multi-process architecture defended against was a crashed or buggy renderer taking down the whole browser or corrupting unrelated tabs' in-process memory — a reliability and blast-radius problem, which plain process separation (Module 5) genuinely solves completely, no integrity levels needed. What this module demonstrates is a different threat model: a maliciously compromised renderer deliberately trying to read another origin's data using legitimate OS APIs. That threat only becomes the priority once you assume an attacker has already achieved code execution inside one renderer (e.g. via a real browser engine bug) and start asking "now what can they reach?" — which is precisely the shift in thinking Spectre forced across the entire industry: not just "can a bug in my code leak my own data" but "can an attacker who already has code execution somewhere reach data they were never supposed to see." This module's Part A is a concrete instance of exactly that second, harder question.

08There Are No Dumb Questions

Doesn't Part A basically mean process isolation is worthless?
No — Module 5's guarantee (no *accidental* cross-talk, no address-collision risk) is still completely real and still matters enormously. This module adds a second, separate claim on top: process separation doesn't automatically stop a *deliberate*, privileged attempt. Both things are true at once; conflating them is the exact mistake this module exists to prevent.
Why does Windows treat process/thread objects specially for "no read up," when Module 9 showed ordinary files allow read-up by default?
Because the potential harm is different in kind. A file's contents are whatever the file happens to contain — often intentionally shareable. A process's live memory can contain anything currently being computed: passwords mid-entry, decrypted data, cryptographic keys. Microsoft's default policy reflects that higher sensitivity specifically for process/thread objects, even though it left the more general "any object" default more permissive.
Would Part B still succeed if the victim were also Low integrity (not Medium)?
Yes — MIC's "no read up" only blocks reads where the target is at a higher integrity than the reader; two processes at the same integrity level don't trigger it. This is precisely why real sandboxes don't rely on integrity level alone to separate same-privileged components from each other — they add restricted tokens, distinct AppContainer SIDs, or Job Object restrictions on top, exactly as flagged in this module's Limits section.
Is this technique ever legitimate outside of attacks?
Constantly — debuggers, profilers, and diagnostic tools all use exactly OpenProcess/ReadProcessMemory legitimately. The API itself is neutral; what matters is the access control decision governing when it's allowed to succeed, which is this module's entire subject.
