TRACK 1 · PHASE 4 · MODULE 13 · FIRST C MODULE

dep_nx_w_xor_x

Proves: DEP/W^X is not a heuristic — identical machine code bytes, identical logic, and the CPU's decision to allow or kill execution depends on exactly one thing: whether the OS was told, in advance, that this specific page may contain code.

00Prerequisites

page permission bits Module 2: privilege_rings

01The Big Analogy

A commercial kitchen has two areas: the prep counter (where ingredients get chopped — "data") and the actual stove (where cooking — "execution" — happens). A health inspector's rule is simple and absolute: nothing gets cooked anywhere except a stove, full stop, no matter how ready-to-cook it looks sitting on the prep counter. It doesn't matter if someone arranges raw ingredients on the counter in the exact shape of a finished dish — the counter is not a heat source, and no amount of clever arrangement changes that. If you want something cooked, it has to be physically moved to a stove first. DEP is that same absolute, structural rule, enforced by the one thing capable of actually enforcing it: the CPU itself.

02What Happens, Step by Step

  1. dep_violation.c hand-assembles six real x86-64 bytes — a complete function that returns 42 — and copies them into memory from malloc(): ordinary heap memory, READ+WRITE.
  2. It casts that memory to a function pointer and calls it.
  3. The CPU begins fetching instructions from that address — and its page-table-consulted execute-permission bit says no. Windows raises an access violation; the process is terminated.
  4. dep_legitimate_jit.c writes the identical six bytes, but into memory obtained via VirtualAlloc with PAGE_EXECUTE_READWRITE explicitly requested.
  5. The identical jump-and-call succeeds. The function runs, returns 42, and the program exits cleanly.

03What We Actually Captured

=== Running dep_legitimate_jit.exe (VirtualAlloc'd, PAGE_EXECUTE_READWRITE) ===
Wrote 6 bytes of the SAME machine code into a VirtualAlloc'd, PAGE_EXECUTE_READWRITE region at 0000029ce0e70000

Returned cleanly. Result: 42 (expected 42)

Real, captured output — confirmed both directly and via PowerShell's $LASTEXITCODE, which showed the identical value as the signed NTSTATUS -1073741819.

04The Code, Explained

unsigned char code[] = { 0xB8, 0x2A, 0x00, 0x00, 0x00, 0xC3 }; /* mov eax,42; ret */
unsigned char *buffer = malloc(sizeof(code));
memcpy(buffer, code, sizeof(code));
func_ptr f = (func_ptr)buffer;
int result = f();  /* crashes here */

Every one of those six bytes is a real, meaningful x86-64 instruction encoding — not a placeholder. The only thing separating this crashing program from the working one is which allocator supplied the memory, and therefore what permission bits the page table entry for that memory carries. Same bytes, same cast, same call — different fate, decided entirely by the page's own metadata.

07Brain Exercise

A JavaScript engine's JIT compiler needs pages that are, at different moments, WRITABLE (while the JIT is generating code) and EXECUTABLE (once it's ready to run). Given this module's strict data-vs-code split, how should a security-conscious JIT actually manage that page's permissions over time? Think about what "W^X" (write XOR execute) as a stricter rule implies, before revealing the answer.
It should never leave the page BOTH writable and executable at the same time. The safe pattern — literally named "W^X," write XOR execute — is: allocate the page as writable (not executable), write the generated code into it, then explicitly call VirtualProtect to flip it to executable-and-NOT-writable before ever running it. If new code needs to be written later, flip it back to writable-not-executable first. This module's dep_legitimate_jit.c deliberately used the LOOSER PAGE_EXECUTE_READWRITE (writable AND executable simultaneously) specifically because that's simpler to demonstrate — but it's exactly the pattern real hardened JIT compilers avoid, because a page that's both writable and executable at once is a much easier target if an attacker ever manages to write to it unexpectedly: they get to inject code AND run it through the same permission window, with no separate "flip to executable" step to interfere with.

08There Are No Dumb Questions

Why does the crashing program's exit code look like a huge number instead of something small like 1 or -1?
Because it isn't an exit code the program chose — it's the NTSTATUS value of the exception that killed it, which Windows uses directly as the process's exit code when no handler catches the fault. 0xC0000005 is Microsoft's own defined constant for STATUS_ACCESS_VIOLATION, the same value you'd see in Event Viewer for any application crash of this type.
Would this crash happen on a 32-bit build too?
Historically, DEP had per-application opt-out mechanisms on 32-bit Windows for compatibility with old software that relied on executing writable memory. 64-bit Windows removed that opt-out for 64-bit processes — DEP/NX enforcement is a permanent, non-optional property of running as a 64-bit process, which is part of why this course, per the ROADMAP's tools decision, targets 64-bit builds throughout.
Is the malloc'd buffer ever executable on ANY system?
Not on any system with a working NX/DEP-equivalent enforcement, which includes essentially all mainstream 64-bit CPUs and OSes today. Extremely old CPUs predating the NX bit (pre-2004-era x86 hardware) genuinely had no hardware mechanism to prevent this — DEP is fundamentally a hardware feature the OS merely turns on and enforces via page tables, not something the OS invents from nothing.
Why not just always use PAGE_EXECUTE_READWRITE everywhere and avoid crashes entirely?
Because that would defeat the entire point — it would mean every writable page in your process is also a potential place to run injected code, exactly the scenario DEP exists to prevent. The "inconvenience" of needing to explicitly request executable memory is the security property, not an accident to work around.
