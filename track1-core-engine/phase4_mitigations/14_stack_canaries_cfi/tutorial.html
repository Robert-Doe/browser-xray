stack_canaries_cfi

Proves: a stack canary catches control-flow hijacking at one specific checkpoint — right before a corrupted return address gets used — by building a real overflow bug and watching the same corruption produce two very different outcomes.

00Prerequisites

Module 13: dep_nx_w_xor_x stack basics (implicit in process anatomy)

01The Big Analogy

A postal sorting facility places a brightly colored, easily disturbed tissue-paper seal across the opening of every high-value package tray, right where the tray closes before shipping. Nobody's watching every package get loaded — the seal doesn't stop anyone from overstuffing a tray. But the instant before that tray ships out the door, one worker glances at the seal. Torn seal? The tray never leaves the building — whatever's happened to its contents, it happened, but it goes no further. Intact seal? The tray ships, trusted, no further questions asked. The seal doesn't prevent tampering. It prevents tampered contents from ever leaving the building undetected — checked at exactly one moment, right before the point of no return.

02What Happens, Step by Step

  1. vulnerable() declares a 16-byte stack buffer and copies its argument into it with strcpy — no bounds check at all.
  2. Compiled WITH a stack protector, the compiler places a random "canary" value between the buffer and the saved return address, and inserts a check of that value right before the function returns.
  3. Given a short input, nothing overflows, the canary is untouched, the check passes silently, the function returns normally.
  4. Given a long input, strcpy overflows past buf, overwriting the canary (and likely the return address too) with attacker-supplied bytes.
  5. At the return checkpoint, the canary check fails — the runtime calls __stack_chk_fail, prints a warning, and terminates the process immediately, before the corrupted return address is ever used.
  6. Compiled WITHOUT a stack protector, the identical overflow happens — but there's no checkpoint. The function proceeds straight to return, which uses the now-corrupted return address, jumping to invalid memory and crashing there instead.

03What We Actually Captured

=== overflow_protected.exe, SHORT input (no overflow) ===
  exit code: 0 (0x00000000)

=== overflow_protected.exe, LONG input (overflows into the canary) ===
*** stack smashing detected ***: terminated
  exit code: 3221226505 (0xC0000409) -> STATUS_STACK_BUFFER_OVERRUN

=== overflow_unprotected.exe, LONG input (identical overflow, no canary) ===
  exit code: 3221225477 (0xC0000005) -> STATUS_ACCESS_VIOLATION
Real, captured output — three runs of the identical source file's same bug, differing only in a compiler flag and an input length.

04The Code, Explained

void vulnerable(const char *input) {
    char buf[16];
    strcpy(buf, input);  /* THE BUG: no bounds check whatsoever */
    printf("  strcpy completed. buf now contains: %s\n", buf);
}

Everything you need to understand the vulnerability is in that one line — strcpy copies until it hits a null terminator in input, with zero awareness of how big buf actually is. Nothing about this function knows or checks the length. The compiler flag (-fstack-protector-all vs. -fno-stack-protector) is the ONLY thing that differed between the protected and unprotected builds — the bug itself is identical in both.

07Brain Exercise

This module's overflow always corrupts the canary AND the return address together, because they sit next to each other on the stack. Could a DIFFERENT kind of bug corrupt a return address (or a function pointer) WITHOUT ever touching a canary at all — making the canary blind to it? Think about what the canary actually checks, and when, before revealing the answer.
Yes — and this is precisely the real, historical motivation for Control Flow Integrity (CFI) mechanisms going beyond stack canaries. A canary only detects corruption that happens to land ON the canary's own stack position, checked only at one function's return. A bug that corrupts a function pointer stored on the HEAP (not the stack), or a vtable pointer in a C++ object, or a return address reached via a completely different bug class (like a format-string vulnerability that writes to an arbitrary address, not a linear overflow that happens to spill past a local buffer) — none of these necessarily touch any canary at all, and a canary-only defense has nothing to say about them. This is exactly why real hardened systems layer CFI mechanisms (which validate that indirect calls/returns land on legitimate targets, checked at the point of the jump itself, not via a separate nearby value) on top of stack canaries — canaries and CFI catch overlapping but genuinely different attack shapes. This course does not build a working CFI mechanism (a real one requires compiler and/or hardware support well beyond a toy demo), but naming the gap precisely is itself real, useful knowledge.

08There Are No Dumb Questions

Why does the unprotected build crash at all, if there's no canary to stop it?
Because the corrupted return address itself is garbage (built from repeated 0x41 ['A'] bytes) — the CPU tries to jump execution there when the function returns, and that address isn't validly mapped in the process, producing an ordinary access violation. A real attacker crafts the overflow bytes to land on a specific, meaningful address instead of random 'A's — this module deliberately never does that (see SAFETY_NOTES.md).
Is a stack canary the same thing as ASLR (Module 12)?
No, and they protect against different things in different ways: ASLR makes addresses hard to predict in advance; a stack canary detects that a linear overflow already happened, regardless of whether any address was predictable. They're complementary, independent layers — a real hardened build uses both simultaneously, along with DEP (Module 13).
What does "*** stack smashing detected ***" actually check?
A random value the compiler placed on the stack when the function was entered, compared against its expected value right before the function returns. If they don't match, something wrote past where it should have — the runtime has no way to know exactly what was corrupted, only that the boundary was crossed, which is why the only safe response is immediate termination rather than trying to "fix" or continue.
Could the canary value itself be predicted or leaked, defeating this protection the way Module 12 defeated ASLR?
In principle, yes — a separate information leak that reveals the canary's actual value would let a sufficiently careful overflow write the correct value back in place, passing the check despite real corruption elsewhere. This is a real, known category of canary-bypass technique in security research, following exactly the same "one leak undoes a randomization-based protection" pattern Module 12 demonstrated — a nice, concrete link between these two Phase 4 modules.
