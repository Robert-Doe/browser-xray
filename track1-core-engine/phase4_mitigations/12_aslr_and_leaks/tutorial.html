TRACK 1 · PHASE 4 · MODULE 12

aslr_and_leaks

Proves: ASLR raises the cost of an exploit by making addresses unpredictable across runs — and proves that a single real information leak removes that protection completely, instantly, because everything else is a fixed, learnable offset away.

00Prerequisites

ASLR Module 1: mem_addressing Module 11: site_isolation_model

01The Big Analogy

A bank vault's location within a large, windowless building changes every single day — reception is at a new, randomly chosen spot each morning too, but critically, the vault is ALWAYS exactly 47 doors down the hall from reception, every day, without exception, because that's just how the building's floor plan works. Not knowing where reception is today makes the vault effectively unfindable. But the instant someone glimpses today's reception desk — even by accident, even just a glance through a window — the "47 doors down" rule they memorized years ago hands them the vault immediately. The daily reshuffling was real security, right up until one glimpse.

02What Happens, Step by Step

  1. A "vulnerable" toy program allocates memory at an address Windows chooses (ASLR active), writes a secret at a fixed distance from that base, and — due to a simulated bug — prints the base address as a "diagnostic pointer" (but never the secret's address directly).
  2. We run this program once, note its address, and let it exit — standing in for "an address an attacker learned at some point in the past."
  3. We run it again, fresh — a new process, a new ASLR-randomized base address, kept alive this time.
  4. Part A: the attacker tries the OLD run's address plus the known fixed offset, against the NEW run's live process.
  5. It fails — that address isn't even validly mapped in the new process.
  6. Part B: the attacker tries the SAME formula, using the NEW run's own, freshly leaked address.
  7. It succeeds immediately — the exact secret comes back.

03What We Actually Captured

[reference run] diagnostic pointer was 0x2746CA00000 (this process has now exited)
[live target] PID=32352, THIS run's real diagnostic pointer=0x21893320000

--- Part A (STALE address from a previous run): guessing secret at 0x2746CA02000 ---
[attacker] tried 0x2746CA02000 -- ReadProcessMemory FAILED (GetLastError=299); likely unmapped memory

--- Part B (FRESH address, leaked from THIS run): guessing secret at 0x21893322000 ---
[attacker] tried 0x21893322000 -- read succeeded: b'REAL_SECRET_PAYLOAD_FOUND_ME\x00\x00\x00\x00'
[attacker] landed on the real secret? True
Real, captured output. Same formula, same offset — the stale base failed outright, the fresh leaked base worked on the first try.

04The Code, Explained

secret_address = base + SECRET_OFFSET
ctypes.memmove(secret_address, SECRET_VALUE, len(SECRET_VALUE))
...
print(f"DIAGNOSTIC_POINTER=0x{base:X}")   # the bug: reveals `base`, never `secret_address`

SECRET_OFFSET never changes and is never secret — it's baked into the program, exactly the way a real binary's internal layout is a fixed property of that binary, learnable once by studying it. The only thing ASLR ever protected was base itself. The moment base leaks, the fixed offset does the rest of the attacker's work for free.

07Brain Exercise

Suppose a program had ASLR enabled AND fixed the "diagnostic pointer" bug (never leaks any address) — but still had the underlying memory-corruption bug that let an attacker corrupt the secret if they knew where it was. Is that program now safe from this attack? Think about what else could still go wrong, before revealing the answer.
Not necessarily safe — just harder to attack, which is exactly ASLR's real, honest promise (raising cost, not eliminating risk). Removing this one obvious leak closes this specific path, but an attacker with a memory-corruption bug often has other ways to find an address: brute-forcing across many attempts if the program doesn't crash-and-restart with fresh randomization each time (a real, historically significant weakness in some network services), exploiting a completely different leak elsewhere in the program, or using side-channel techniques that infer address information indirectly without ever "printing" it (Module 34's territory). The deeper lesson: ASLR is one layer in a defense-in-depth strategy, not a single fix that makes a memory-corruption bug irrelevant — which is exactly why real systems pair it with DEP/W^X (Module 13) and stack canaries/CFI (Module 14) rather than relying on it alone.

08There Are No Dumb Questions

Why did Part A's failure show "ReadProcessMemory FAILED" instead of just reading the wrong data?
Because the stale address, while numerically plausible, landed outside any memory Windows had actually mapped for the new process's page tables — reading from a completely unmapped address fails outright rather than returning garbage. If it had happened to land inside SOME mapped-but-unrelated region, you'd see the "succeeded but wrong content" case instead — both outcomes equally demonstrate ASLR did its job, just via slightly different failure shapes.
Is a 2^48-ish address space actually hard to brute-force guess?
Yes, dramatically — for a 64-bit process, ASLR's real entropy (the actual number of possible base positions, which is smaller than the theoretical full address space but still very large) makes blind guessing computationally infeasible for a single-shot, crash-if-wrong attack. This is precisely why real attackers pursue information leaks instead of brute force whenever a target has real ASLR.
Does 32-bit ASLR provide the same protection as 64-bit?
No — historically, 32-bit processes have a much smaller address space to randomize within, meaning far less real entropy and a meaningfully higher (though still nontrivial) chance of a lucky blind guess. This is one of several real reasons 64-bit software is considered to have a stronger ASLR posture than 32-bit, independent of any other factor.
Could this exact leak-plus-offset pattern apply inside a browser's JavaScript engine?
Yes — this is a well-known real category of browser vulnerability: a JS engine bug that lets script code read a raw pointer value (e.g. via a type-confusion bug exposing an internal object's address to JavaScript) gives an attacker exactly the "leaked base" this module simulates, often followed by exactly this kind of fixed-offset computation to locate other sensitive engine structures.
