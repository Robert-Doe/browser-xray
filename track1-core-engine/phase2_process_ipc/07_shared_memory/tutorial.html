shared_memory

Proves: shared memory is the one deliberate exception to process isolation — two processes really do see the same physical bytes, live, no copying — and that "must be opted into by both sides" has a sharper, quieter failure mode here than it did for pipes and sockets.

00Prerequisites

01The Big Analogy

Module 6's pipes and sockets were like a walkie-talkie: you speak, it's relayed, the other person hears a copy of your words a moment later. Shared memory is like two people writing on the same physical whiteboard, from two different rooms, through a shared wall with a hole cut exactly to line up — anything either of them writes is just there, immediately, for the other to see, no "sending" involved. But there's a catch this analogy demands you notice: that hole in the wall only exists if both rooms' builders agreed on its exact location. Get the measurement wrong by an inch, and each room quietly gets its own solid, private wall instead — with no alarm going off telling either builder they missed.

02What Happens, Step by Step

  1. The writer process creates a named, pagefile-backed shared memory segment — Windows' CreateFileMapping, wrapped by Python's mmap module — and writes a string into it.
  2. The reader process maps a segment using the same name.
  3. Windows hands the reader a view onto the same physical pages the writer is using — not a copy.
  4. The reader sees the writer's string immediately upon mapping, with zero message-passing calls involved.
  5. The reader writes its own string into the same segment.
  6. The still-running writer reads the segment again and sees the reader's update.
  7. Separately, a second reader maps a slightly different name — and gets its own private, empty segment, with no error at all.

Real, captured output. Part A: genuine live, bidirectional sharing. Part B: a name mismatch that produces silence, not an error.

04The Code, Explained

segment = mmap.mmap(-1, SIZE, tagname=tagname)
current = bytes(segment[:64]).split(b"\x00", 1)[0]

The -1 file descriptor tells mmap "back this with the system paging file, not a real file on disk" — this is what makes it pure shared memory rather than a shared-file mapping. Under the hood this is Windows' CreateFileMapping(INVALID_HANDLE_VALUE, ...) followed by MapViewOfFile, the same pair of calls a C or C++ program would use directly. Python's standard library is calling the real OS mechanism, not simulating sharing at the language level.

07Brain Exercise

Given what Part B just showed — a name mismatch silently produces two unrelated private segments, no error — would you expect this class of bug to be EASIER or HARDER to debug in a real system than a Module-6-style "connection refused" bug? Think about what each failure actually looks like to a developer before revealing the answer.
Harder — often much harder. A "connection refused" error points you almost directly at the problem: something threw an exception, with a clear message, at the exact moment the mismatch mattered. A shared-memory name mismatch produces no exception anywhere. Instead, you get a program that runs "successfully," produces wrong or stale-looking results, and gives no direct signal about why. You'd likely spend time suspecting a logic bug, a race condition, or stale caching before ever suspecting "these two components are silently talking to two different memory regions." This is a genuinely important, transferable debugging instinct: failure modes that are silent and "successful-looking" are systematically more expensive to diagnose than failure modes that throw loudly — which is itself a real argument, independent of raw performance, for when a system design should prefer explicit message-passing over shared memory even at some cost.

08There Are No Dumb Questions

Why didn't the demo need any locks, if shared memory needs its own synchronization?
It got away without one because the orchestrator's fixed sleeps happened to serialize the reads and writes correctly for this specific, controlled demo — which is exactly the kind of fragile "it worked, this time, in this order" situation real synchronization primitives (mutexes, atomics, events) exist to make robust instead of lucky. This module intentionally doesn't build that layer, to keep the sharing behavior itself the sole focus.
What's the difference between Local\ and Global\ namespaces?
Local\ scopes the shared segment to the current login session — the normal, least-privileged choice, and what this module uses. Global\ makes it visible system-wide, across all user sessions, and typically requires the SeCreateGlobalPrivilege right — appropriate only when you genuinely need cross-session sharing (uncommon for ordinary applications).
Does real Chromium use shared memory like this?
Yes, extensively — for exactly the performance reason this module's analogy hints at. Bulk data that would be expensive to copy repeatedly (e.g. some rendering/compositing buffers) is passed via shared memory regions, while control messages and anything crossing a real trust boundary typically go over Mojo's message-passing channels instead. The choice between the two, per channel, is a deliberate performance/trust tradeoff — not an accident.
Is the "silent mismatch" behavior specific to Python's mmap, or is it Windows itself?
It's Windows itself — mmap is a thin wrapper here. CreateFileMapping is documented to create a new section if the named one doesn't already exist, rather than failing. This module's Part B is demonstrating real OS behavior, verified directly, not a Python-specific quirk.
