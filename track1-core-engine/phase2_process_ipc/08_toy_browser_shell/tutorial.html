01The Big Analogy

A restaurant's front-of-house manager never cooks. They take an order, walk it to the kitchen, and a specific line cook — one dedicated person, working at their own station with their own tools, not sharing a cutting board with anyone — prepares that one dish and calls back "table 4's order is up." The manager never reaches into the kitchen to grab the food themselves, and the line cook never wanders out to seat guests. Everything crosses the pass window as a spoken order and a spoken "it's ready" — never as the manager grabbing raw ingredients directly off a cook's station. This is the entire shape of a multi-process browser: one coordinating process, dedicated workers who don't share their internals, and everything between them travels as an explicit, spoken message.

02What Happens, Step by Step

  1. The Browser Process starts, opens a TCP listening socket, and for each tab it wants to open, spawns a genuinely separate Renderer Process (Module 5's guarantee: separate address space).
  2. Each Renderer Process connects back to the Browser Process's socket and announces its own PID.
  3. The Browser Process sends that renderer a structured load_url message — length-prefixed JSON, the exact framing ipc_protocol.py defines.
  4. The renderer (today: a stand-in, not a real parser) "renders" the URL and sends back a structured loaded response.
  5. The Browser Process prints each tab's result, attributing it to the specific renderer PID that produced it.
  6. The Browser Process sends each renderer a shutdown message; each renderer acknowledges and exits cleanly.

Notice what's not here: no shared variable, no shared memory, no direct function call from browser code into renderer code. Every single interaction between the Browser Process and a Renderer Process is a message, over a socket, in the exact length-prefixed format ipc_protocol.py defines. This is a real architectural constraint, not a simplification — real Chromium's Browser Process and Renderer Processes are similarly constrained to communicate only through Mojo IPC.

07Brain Exercise

Suppose one Renderer Process crashes mid-render (imagine renderer_process.py raised an unhandled exception right after connecting). What happens to the other tabs' Renderer Processes, given this module's architecture? Think about what is — and isn't — shared between them before revealing the answer.
Nothing happens to them — they keep running completely unaffected. Because each Renderer Process is a genuinely separate OS process (Module 5) with its own address space, a crash in one cannot corrupt another's memory, and because each has its own dedicated socket connection to the Browser Process, one connection breaking doesn't affect the others' message exchange. The Browser Process would simply see that one specific recv_message() call fail (a `ConnectionError`, per ipc_protocol.py's framing code) for that one tab's socket, while the other tabs' sockets remain completely healthy. This is precisely the real-world payoff of the multi-process architecture: "one tab crashed" instead of "the whole browser crashed," which was a genuine, user-visible improvement when Chrome first shipped this architecture in 2008, replacing the single-process model most browsers used before then.

08There Are No Dumb Questions

Why does the renderer need to send a "hello" message with its own PID? Doesn't the Browser Process already know it, from spawning it?
Good catch — subprocess.Popen does return the child's PID (proc.pid) immediately. The "hello" message is deliberately redundant here for a specific teaching reason: it demonstrates that the IPC channel itself carries the renderer's identity, independent of what the Browser Process already knew from spawning it — which matters once modules build stricter identity or capability checks over this same channel later.
Is this actually how many tabs Chromium can open, one process each?
Conceptually yes, though real Chromium applies additional process-reuse heuristics (e.g. grouping same-site tabs, limiting total renderer count under memory pressure) rather than a strict one-process-per-tab rule always. This module's simplified one-per-tab model is the right starting point; Module 11 refines it toward the real, origin-aware policy.
What would happen if two tabs requested the exact same URL?
With this module's code, they'd still get two separate Renderer Processes, each independently "rendering" its own copy — no sharing or deduplication happens. Whether and how a real browser might share resources between same-origin tabs is exactly the kind of nuance Module 11 (Site Isolation) exists to address deliberately, not by accident.
Why length-prefix the JSON instead of just using newline-delimited JSON (one JSON object per line)?
Newline-delimited JSON is a real, valid alternative — and simpler for this exact use case. Length-prefixing was chosen because it generalizes to binary payloads (a real browser IPC message might carry raw bytes, not just text) without needing an escaping scheme, and it's the same framing shape Module 15's HTTP/TLS work will recognize in a different protocol later.
