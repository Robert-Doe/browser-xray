TRACK 1 · PHASE 2 · MODULE 06

pipes_and_sockets

Proves: two isolated processes can only exchange data through a channel both sides deliberately, explicitly set up — by building two working channels (a named pipe, a TCP socket) and then showing both refuse to deliver anything when only one side shows up.

00Prerequisites

IPC as a general idea kernel-mediated channels Module 5: process_creation

01The Big Analogy

A walkie-talkie only works if the person on the other end has their own walkie-talkie, powered on, tuned to your exact channel. Owning a walkie-talkie and knowing "channel 7 exists" gets you nothing by itself — you can key the mic and talk all day into dead air. The channel isn't a place that exists independently, waiting to be found; it's created the moment both sides are actually tuned in together, and it stops existing the moment either side isn't.

02What Happens, Step by Step

  1. The server process creates a named pipe (or binds a TCP socket) at a specific, fixed address — a pipe name, or a (host, port) pair — and waits.
  2. The client process, started as a genuinely separate process, connects to that exact address.
  3. The kernel — which mediates both the pipe and the socket — matches the two up and lets bytes cross.
  4. A message goes from client to server, a reply goes back.
  5. Separately, a client attempts to connect to an address no server ever set up — same code, same logic, different target.
  6. The kernel refuses immediately, because there was never a matching side to connect to.

Real, captured output from both demos. Two different addressing schemes, two different specific refusal behaviors — same underlying claim confirmed both times.

04The Code, Explained

handle = win32file.CreateFile(
    PIPE_NAME, win32file.GENERIC_READ | win32file.GENERIC_WRITE,
    0, None, win32file.OPEN_EXISTING, 0, None,
)

A client connecting to a named pipe uses the same CreateFile function you'd use to open a regular file — Windows treats named pipes as a kind of file in its object-manager namespace. OPEN_EXISTING is the key detail: it tells Windows "only succeed if this already exists," which is exactly why Part B fails the way it does — there's nothing existing to open.

06Run It

cd track1-core-engine/phase2_process_ipc/06_pipes_and_sockets
python run_pipe_demo.py
python run_socket_demo.py
If run_socket_demo.py's Part B prints a ConnectionRefusedError instead of a timeout on your machine — that's also a correct result, not a discrepancy. Which one you see depends on whether something in your local network stack (a firewall, a security product) answers an unused port's SYN with an explicit RST or silently drops it. Both outcomes prove the same thing: no data ever crossed. See DECISIONS.md for the real difference we hit while building this.

07Brain Exercise

A malicious process on your machine knows the exact pipe name a legitimate privileged service uses. Does knowing the name alone let it read that service's traffic? Think about what CreateNamedPipe's security attributes parameter (passed as None in this module) is for, before revealing the answer.
Not necessarily — and this module deliberately left a gap you should notice. We passed None for CreateNamedPipe's security attributes, which means "use default security," letting any process on the machine connect. A real privileged service typically supplies an explicit security descriptor restricting which users/processes may connect at all. Knowing a channel's address (its name, or its host+port) is necessary but not sufficient to use it — the kernel still checks access rights on connection, the same way Module 4's OpenProcess needed explicit granted rights, not just a known PID. This module proved "a channel must be built"; it deliberately did not build the access-control layer on top of that, which is a real, separate concern in production code.

08There Are No Dumb Questions

Why message mode for the pipe instead of byte-stream mode?
Simplicity for this specific demo — see DECISIONS.md. Message mode guarantees one WriteFile call is received by exactly one matching ReadFile call, so we don't have to handle partial reads to make the point clearly.
Is a named pipe "faster" than a TCP socket on the same machine?
Generally yes, for local-only communication — a named pipe avoids the TCP/IP stack's overhead (sequencing, checksums, flow control) entirely, since it's a more direct OS-level construct. This module doesn't benchmark that difference, but it's a real, well-known reason real systems (including parts of Windows itself) prefer named pipes or similar local-only IPC over loopback sockets when both endpoints are guaranteed to be on the same machine.
Does Chromium's Mojo actually use named pipes or sockets?
Mojo's underlying transport is platform-specific and can use several primitives depending on platform and need — including named pipes on Windows and Unix domain sockets on POSIX systems — but the architectural point this module makes (explicit, kernel-mediated, mutually-established channels) holds regardless of which specific primitive is underneath.
Why bind the TCP server to 127.0.0.1 and not 0.0.0.0?
Safety and scope — binding to 0.0.0.0 would make the demo server reachable from other machines on the network, which this module has no reason to do and deliberately avoids (see SAFETY_NOTES.md).
