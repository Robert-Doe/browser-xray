TRACK 1 · PHASE 2 · MODULE 05

process_creation

Proves: spawning a child process creates a genuinely separate address space — by forcing a parent and a freshly spawned child to both claim the identical numeric virtual address, and watching them never once collide.

00Prerequisites

virtual address space why processes exist as a split from threads Module 1: mem_addressing

01The Big Analogy

Two identical safety deposit boxes, both labeled "Box 7," sit in two completely different bank branches across town. You put cash in "Box 7" at Branch A. Someone else puts a different envelope in "Box 7" at Branch B. The label matching doesn't create any connection between the boxes — they were never the same box, just two boxes that happen to share a number, in two buildings that have nothing to do with each other. You could open your Branch A box a year later and your cash is exactly as you left it, utterly unaffected by whatever happened at Branch B's "Box 7" in the meantime.

02What Happens, Step by Step

  1. The parent process calls VirtualAlloc with a specific, non-NULL address — asking Windows for that exact virtual address, not "any free address."
  2. It writes a known string into that memory.
  3. It spawns a child process via subprocess.run (which ultimately calls Windows' CreateProcess) — a genuinely new process, with the OS building it a fresh, empty address space from scratch.
  4. The child asks for the identical numeric address the parent used. Windows grants it — because in the child's own, separate address space, that address was never taken.
  5. Before writing anything, the child reads what's at that address — and finds all zero bytes, not the parent's string, because freshly committed memory is documented to start zeroed.
  6. The child writes its own, different string, then exits.
  7. The parent — still running the whole time — reads its own copy at that same address one more time.

03What We Actually Captured

[parent] claimed virtual address 0x200000000000
[parent] wrote: b'PARENT_WROTE_THIS_VALUE_1234\x00'

[child] claimed the SAME virtual address as the parent: 0x200000000000
[child] bytes found at that address BEFORE writing anything: b'\x00\x00\x00...\x00'
[child] bytes at that address AFTER this process wrote to it: b'CHILD_WROTE_THIS_VALUE_5678\x00'

[parent] re-reading MY OWN copy at 0x200000000000 after the child ran and wrote to 'the same' address:
[parent] bytes found: b'PARENT_WROTE_THIS_VALUE_1234\x00'
[parent] unchanged from what I originally wrote? True
Real, captured output. Identical address number, three completely independent observations of it.

04The Code, Explained

got = kernel32.VirtualAlloc(
    ctypes.c_void_p(PINNED_ADDRESS), PINNED_SIZE,
    MEM_COMMIT | MEM_RESERVE, PAGE_READWRITE
)
if got != PINNED_ADDRESS:
    raise RuntimeError("OS granted a different address than requested")

The whole experiment depends on this one behavior: VirtualAlloc with a non-NULL address either gives you exactly that address or fails outright — it never silently substitutes a nearby free one. That's what lets us force two unrelated processes onto the same number on purpose, instead of hoping for a coincidence.

07Brain Exercise

Suppose, instead of subprocess.run, the parent had started the child using Python's threading module instead — running the "child" logic as a new thread in the same process. Would this experiment still show isolation? Think it through before revealing the answer.
No — and that's exactly the point of the process/thread distinction from Prerequisite 4. A thread shares its parent's address space completely. If the "child" were a thread instead of a process, both the "parent" and "child" logic would be reading and writing the same physical memory at that address — the second write would simply overwrite the first, and the "parent" would see the thread's string when it re-read the address. The entire experiment only demonstrates isolation because a process boundary, not a thread boundary, sits between the two writers. This is precisely why the multi-process browser architecture (Modules 8 and 11) chooses processes, not threads, as its isolation unit — threads wouldn't provide this guarantee at all.

08There Are No Dumb Questions

Why does the address have to be so large (32 TB)?
It doesn't have to be — any address free in both processes would work. A large, unusual value was chosen because it's reliably far from anything a normal process's loader, heap, or stack would ever use, making the exact-address request succeed consistently rather than occasionally failing due to ASLR placing something else there.
Doesn't this contradict ASLR (Module 1), which randomizes addresses?
No — VirtualAlloc with an explicit address is a deliberate override of the "let the OS pick" default that ASLR governs. ASLR randomizes addresses the OS chooses on your behalf (like where the heap or a DLL loads); it doesn't prevent your own code from explicitly requesting a specific address, if that address happens to be free.
What would it actually look like if isolation were broken?
The parent's final read would show b'CHILD_WROTE_THIS_VALUE_5678\x00' instead of its own string — meaning the child's write reached the parent's physical memory. That's precisely the failure condition parent_writes.py checks for and would raise an error on, and it's precisely the property real vulnerabilities like certain virtualization/hypervisor escape bugs have historically broken, at a different layer than plain OS process isolation.
Is this the same mechanism Site Isolation (Module 11) relies on?
Yes, at its foundation — Site Isolation's core guarantee ("a compromised renderer for origin A can't read origin B's data") is built on exactly this OS-level process isolation property, applied deliberately: putting different origins in different OS processes. Module 11 adds the origin-to-process assignment policy on top of the isolation this module already proved.
