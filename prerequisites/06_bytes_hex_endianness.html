Bytes, Hex, and Endianness

Say you write the number "one thousand two hundred thirty-four" on index cards, one digit per card: 1, 2, 3, 4. Now imagine two librarians filing multi-card numbers on a shelf. Librarian A always files the most significant card first (the way you read it: 1-2-3-4). Librarian B always files the least significant card first (4-3-2-1) because their filing convention finds it easier to grab the "ones" card quickest. Both librarians agree perfectly on what number is stored — but if you peek at Librarian B's shelf expecting Librarian A's order, you'll misread 1234 as 4321. Neither is "wrong." They're different, mutually understood conventions, and you have to know which one you're looking at.

A byte is 8 bits, and its value is almost always written in hexadecimal (base 16) because it maps perfectly: one hex digit = 4 bits, so a byte is always exactly two hex digits, from 0x00 to 0xFF. This isn't a stylistic choice — decimal doesn't divide evenly into bit groups, hex does, which is why every memory dump, every protocol spec, every debugger you'll ever use shows hex, not decimal.

Reading Hex Fluently

You don't need to convert hex to decimal in your head to be fluent — you need pattern recognition. 0x00 is all-zero bits. 0xFF is all-one bits (a full byte). 0x7F is the largest positive value a signed byte can hold (0111 1111) — 0x80 flips the sign bit and becomes the most negative value in two's-complement. Addresses are typically shown as 8 or 16 hex digits (32-bit or 64-bit). None of this needs memorizing tables — it needs enough repeated exposure (which the modules provide) that the shapes become familiar the way word shapes are to a fluent reader.

Endianness: The Order Multi-Byte Values Are Stored In

A single byte has no ordering ambiguity. But a 4-byte integer, like the value 1 stored as a 32-bit int, occupies four consecutive memory addresses — and there are two competing conventions for which byte goes first:

  • Little-endian: least-significant byte at the lowest address. The value 1 as a 32-bit int is stored as bytes 01 00 00 00. This is what x86 and x86-64 CPUs use — meaning it's what your own machine uses natively.
  • Big-endian: most-significant byte at the lowest address. The value 1 is stored as 00 00 00 01. This is what network protocols conventionally use — often called "network byte order."
Identical value, two byte orders. If Module 15 or 19 shows you a hex dump that looks "backwards," check which convention applies.

Why This Matters for This Course Specifically

Module 15 has you read real bytes off a live TCP/TLS handshake, and protocol headers (IP, TCP, DNS) are defined in network byte order (big-endian), while any address you print from Python or the debugger on your own x86-64 machine is little-endian. Getting this backwards is the single most common reason a "the byte values don't match what I expected" confusion happens — and it's never a bug in the demo, it's a byte-order mismatch in your own reading.

Python's struct module makes this explicit rather than implicit: struct.pack('<I', x) forces little-endian, struct.pack('>I', x) forces big-endian (the ! format character is a synonym for network/big-endian). When a module's code uses one of these, that's not an arbitrary choice — it's dictated by whichever spec (a wire protocol vs. your own CPU's native layout) that byte sequence has to match.
