Virtual Memory & Address Spaces

Imagine an apartment building where every tenant is handed a floor plan that says "your apartment is Room 100." All of them. Every tenant's floor plan says Room 100. Nobody's lying — the building superintendent (the OS + the CPU's memory management unit) privately maps each tenant's "Room 100" onto a different real room in the actual building, and swaps the mapping whenever needed. No tenant can even directly address the real room number. They only ever see their own private floor plan.

That's virtual memory. Every process gets its own virtual address space — a full, private range of addresses (on a 64-bit OS, conceptually up to 2⁶⁴ of them) that it treats as if it owns the whole thing. When your code reads or writes address 0x00007FF6A2C31000, that number is never a physical RAM location. It's a request the CPU hands to a piece of hardware called the MMU (Memory Management Unit), which walks page tables — maintained per-process by the OS — to translate it into a real physical address, or faults if there's no valid mapping.

The Address Space Is the Unit of Isolation

This is the single fact this whole course leans on hardest: two processes can use the identical virtual address and touch completely different physical memory, because each process has its own page tables. That's why a compromised process can't just "read across" into another process's memory by guessing an address — the hardware itself has no path from one process's page tables into another's. (Modules 5 and 11 make you watch this happen directly.)

Same virtual address (0x1000), two different processes, two different — and mutually invisible — physical pages.

Pages, and Why Memory Comes in Fixed Chunks

The OS doesn't map memory one byte at a time — that would need an absurd amount of bookkeeping. It maps in fixed-size chunks called pages (4 KB is the classic default on both Windows and Linux on x86-64). A page table entry says "this virtual page maps to this physical page" and carries permission bits alongside that mapping: readable, writable, executable. Those three bits, per page, are the entire hardware foundation of DEP/NX (Module 13) — the CPU will physically refuse to execute a page whose executable bit is off, no matter what's in it.

Kernel Space Lives in the Same Address Space, Just Locked

A common misconception: that the kernel is "somewhere else." On most systems, the kernel's code and data are mapped into the same virtual address space as every user process, in a high region of the address range — it's just marked so that only privileged (ring 0) code can touch it. Your process can't read kernel memory not because it's in a different universe, but because the page table entries for that region are flagged supervisor-only, and the CPU enforces that flag on every single memory access. (This connects directly to Privilege Rings.)

ASLR: Randomizing Where Things Land

If your program's stack, heap, and loaded libraries landed at the exact same virtual addresses on every run, an attacker who found one exploitable bug could hard-code every address they need. ASLR (Address Space Layout Randomization) randomizes the base addresses of these regions each time a process starts, so a memory corruption bug alone isn't enough — the attacker also needs to learn where things actually landed this run. Module 12 has you watch ASLR do exactly this, then watch a single info-leak undo it.

If two runs of the same program print different addresses for the same variable, that's not a bug in the demo — that's ASLR working correctly. If you need reproducible addresses for teaching purposes, that's a deliberate flag to disable ASLR for that one run, never assume it's "normally off."
