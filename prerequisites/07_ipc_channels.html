IPC Channels (the general idea)

Two soundproofed rooms, no doors, no windows. The only way anyone in Room A can get information to Room B is if someone, in advance, installs a phone line between them — and both rooms have to agree on it: A has to pick up and dial, B has to be listening on the other end. Once installed, the phone line does not let Room A wander around Room B's furniture. It only carries what gets deliberately said down the line, in whatever format both sides agreed to speak.

Two processes cannot see each other's memory — that's the entire point of process isolation. So the only way two processes can exchange information at all is Inter-Process Communication (IPC): a deliberately established channel, set up through the kernel, that both sides opted into. There is no "default" channel. Silence is the default; a channel is always a specific, constructed exception to it.

Every IPC Mechanism Is a Variation on One Idea

Whatever the mechanism — a pipe, a socket, a memory-mapped file, a Windows named event, Chromium's own Mojo IPC layer — the shared shape is always: the kernel mediates a channel that both processes explicitly hold a handle to. The differences are about how data crosses:

  • Message passing (pipes, sockets, Mojo messages): one side writes a chunk of bytes, the kernel copies or queues it, the other side reads it. No memory is actually shared — data is copied across the boundary.
  • Shared memory (memory-mapped files/sections): both processes map the same physical pages into their own address spaces, so writes by one are immediately visible to the other with no copy — but now both sides need their own agreed-upon synchronization (locks, atomics) since there's no message ordering to rely on.
Whatever sits in the middle box (pipe, socket, shared segment, Mojo) — it exists only because both ends explicitly built it.

Why "Kernel-Mediated" Is the Important Word

Because the channel is set up through syscalls and represented by kernel-tracked handles, the kernel can see, filter, or refuse it — the same way it can filter any other syscall. A sandboxing policy (Module 10) can say "this process may write to its one designated pipe handle but may not create new sockets" — and that's enforceable precisely because every channel-creation and every send/receive operation passes back through the syscall boundary where a policy can intercept it.

Why the Toy Browser Uses Message Passing, Not Shared Memory

Module 8 builds the Browser Process ↔ Renderer Process link as message passing (a socket), not shared memory — and that's not arbitrary. Message passing means the Browser Process's own memory is never mapped into the Renderer Process at all; the Renderer literally cannot read Browser-process memory through the channel even if it tries, because no address the Renderer holds refers to any of it. Real Chromium uses exactly this reasoning for its Mojo IPC boundary between the privileged Browser Process and the sandboxed, less trusted Renderer Process — sharing memory across that specific trust boundary would undercut the isolation the two-process split exists to provide.

"IPC" is not one specific API — it's a category. If a module or a conversation says "they communicate via IPC" without naming the actual mechanism (pipe? socket? shared memory? Mojo?), that's an incomplete claim — always ask which variant, since the security properties differ meaningfully between message passing and shared memory.
