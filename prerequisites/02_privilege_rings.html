Privilege Rings (Kernel Mode vs. User Mode)

A hotel has guest rooms and a master keycard room. Guests hold a keycard that opens their own room and common areas — never the master room, never anyone else's room. It doesn't matter how badly a guest wants into Room 214; the card reader itself refuses the card. The hardware of the lock enforces the boundary. No guest, however clever, can "argue" their way past a door whose lock simply won't accept their card's bits.

Your CPU has an actual hardware register — on x86-64 it's encoded in the segment selector's low bits, generally referred to as the Current Privilege Level (CPL) — that says what mode the currently executing code is running in. Conceptually there are up to four "rings" (0–3), but in practice every mainstream OS (Windows, Linux, macOS) uses exactly two: Ring 0 (kernel mode) and Ring 3 (user mode).

What Ring 0 Can Do That Ring 3 Cannot

Certain CPU instructions are defined as privileged: executing them while the CPL says "Ring 3" causes an immediate hardware fault — the instruction never runs. Examples: instructions that change page table base registers, that mask hardware interrupts, that read/write certain model-specific registers, or that halt the CPU. Your browser's JavaScript, your Python script, literally every line of every user-mode program you have ever written runs at Ring 3 and has never once executed a privileged instruction directly.

It's Enforced By Hardware, Not by the OS's Goodwill

This is the detail people miss: the restriction isn't a polite convention the operating system asks programs to follow. It's wired into the CPU. If Ring-3 code executes a privileged instruction, the CPU itself raises a general protection fault before a single side effect happens. The OS never has to "catch" a rule violation after the fact — the hardware refuses the action outright. That's what makes it a real security boundary and not a social one.

Ring 3 code can only reach Ring 0 through one controlled gate: the system call (see Prerequisite 3). There is no direct path inward.

The Only Way In Is a Trap

So how does user-mode code ever get the kernel to do something on its behalf — open a file, allocate memory, send a network packet? It executes a special instruction (on x86-64, syscall; the older mechanism was software interrupt int 0x80 on Linux) that deliberately, safely transitions the CPU into Ring 0 at one specific, kernel-controlled entry point. The kernel — not the calling program — decides what happens next. This controlled transition is exactly what a "system call" is, covered next.

"Administrator" or "root" is not the same thing as Ring 0. An Administrator-owned process on Windows still runs its normal code in Ring 3 — being an admin changes what the kernel will permit when that process makes a system call, not what CPU ring the process executes in. Conflating "has admin rights" with "runs in kernel mode" is one of the most common wrong mental models in security discussions — keep them separate.
