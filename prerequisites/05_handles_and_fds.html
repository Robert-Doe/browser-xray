Handles & File Descriptors

A hotel doesn't hand guests a physical master key to their room. It hands them a keycard that means nothing on its own — the front desk's system maps "keycard #4471" to "Room 214, valid until Thursday." Lose the card, the hotel deactivates that number; it never had to change the room's lock. And critically: the front desk can issue a keycard that opens the room but not the minibar, or that expires the moment you leave the front desk. The card is an indirect, revocable, restrictable reference — never the thing itself.

When your process opens a file, a socket, a process, or almost any other OS resource, you never get a direct pointer to that resource. You get back an opaque number — on Windows, a HANDLE; on POSIX systems (Linux/macOS), a small integer called a file descriptor (fd). That number is meaningless outside your process. It's an index into a table the kernel maintains, per process, mapping "handle #3 in this process" to "the real, kernel-side resource object."

The Handle Table Is Per-Process and Kernel-Owned

This indirection is exactly why one process's handle number is garbage in another process — Process A's handle 0x38 and Process B's handle 0x38 can point to two completely unrelated kernel objects, or to nothing at all. It also means the kernel can freely revoke, audit, or restrict access at the handle layer without the underlying resource ever knowing.

Handles Carry Access Rights, Not Just Identity

A handle isn't just "a reference to file X." On Windows, a handle is created with a specific access mask — e.g. GENERIC_READ only, no write, no delete — decided at the moment the handle is created (often via CreateFile or DuplicateHandle). The kernel checks that access mask on every operation you attempt through that handle. This is the exact mechanism Module 9 exploits deliberately: you can spawn a process, then hand it a handle to a resource with fewer rights than you yourself have.

The number in your process is opaque. What it grants access to, and with what rights, is decided entirely by the kernel-side table.

Handles Can Be Inherited or Duplicated Across Processes

When a parent creates a child process, it can choose to make specific handles inheritable, so the child starts with access to exactly those resources — no more. On Windows this is DuplicateHandle/inheritable-handle flags at CreateProcess time; on POSIX it's typically inherited fds across fork(), filtered by the close-on-exec flag. This is the actual mechanism by which a Browser Process can spawn a Renderer Process that holds only the handles the Browser Process chose to share — the seed of every sandboxing module in Track 1, Phase 3.

A process ID (PID) is not a handle. A PID is a plain, guessable, globally-visible integer identity. A handle is an unguessable, per-process, access-scoped reference. Confusing the two is a common source of wrong security reasoning — knowing a PID lets you attempt to request a handle to that process, subject to permission checks; it does not itself grant access.
