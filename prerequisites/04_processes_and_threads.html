Processes vs. Threads

A process is a whole house: its own address, its own locked front door, its own utilities, its own mail. A thread is a person living inside that house. A house can have several people living in it (multiple threads), and they freely share the fridge, the living room, the same front-door key (the process's memory, file handles, address space) — but a person from House A cannot casually stroll into House B's kitchen. They live at a different address, and its door doesn't recognize their key.

A process is the OS's unit of isolation: it owns one virtual address space, one set of open handles, and is described in the kernel by a data structure (Windows calls it an EPROCESS; Linux calls it a task_struct conceptually grouped under a thread group).

A thread is the OS's unit of execution: it's a sequence of instructions being run, with its own CPU register state and its own stack — but every thread inside a process shares that process's one address space and one set of handles.

Why This Split Exists

If isolation and execution were the same unit, you couldn't have concurrency without paying the full cost of isolation for every concurrent task, and you couldn't share memory between cooperating tasks without breaking isolation entirely. Splitting them lets an OS offer both: cheap, fast, shared-memory concurrency within a process via threads, and expensive, hard isolation between processes.

Threads inside a process share everything. Processes share nothing unless they explicitly set up an IPC channel.

The Process Control Block (PCB)

The kernel tracks each process via a control block holding: its process ID, its page table root, its open handle table, its security context (token, on Windows), and pointers to its threads. This is kernel memory — a user-mode process cannot read or forge its own PCB directly; it can only query pieces of it through syscalls (e.g. OpenProcess + query functions on Windows). Module 4 has you inspect a real process's structure this way.

Context Switching Is Expensive Precisely Because Processes Isolate

Switching the CPU from running one thread to running a thread in a different process requires reloading the page table base register — flushing the CPU's address-translation cache (the TLB) in the process. Switching between two threads of the same process needs none of that, because the address space doesn't change. This is a real, measurable cost, and it's part of why a multi-process browser architecture (many renderer processes) is more expensive than a multi-threaded one — and exactly the tradeoff Chromium made deliberately for security (Module 11).

"Multithreaded" and "multiprocess" solve different problems and are not interchangeable safety mechanisms. A bug in one thread can still corrupt another thread's data in the same process, because they share memory. Only process boundaries give you the hard isolation this course's security modules rely on.
