System Calls

A courtroom has exactly one witness stand. Anyone who wants to submit evidence doesn't walk up to the judge directly — they go through the stand, state their request in a fixed, recognized format, and the judge (who can see and hear every word) decides whether to allow it. You cannot slip evidence to the judge by any other route. Every request goes through the one visible chokepoint, which is exactly what makes the courtroom auditable.

A system call (syscall) is the one sanctioned door from Ring 3 into Ring 0. When your program calls something like open(), read(), or on Windows an underlying NtCreateFile, what actually happens is: your code loads a syscall number and its arguments into specific registers, executes the syscall instruction, the CPU switches to Ring 0 at a fixed kernel entry point, and the kernel's syscall dispatcher looks up that number in a table and runs the matching kernel function. Control returns to Ring 3 only when the kernel decides to hand it back.

Why This Boundary Matters for Security

Every single thing a process does that has an effect outside its own private virtual address space — touching a file, opening a socket, spawning another process, mapping shared memory — has to go through a syscall. That means the syscall boundary is a complete choke point: if you can observe, log, or filter every syscall a process makes, you have complete visibility and control over everything that process can do to the outside world. This is precisely the leverage point Modules 3 and 10 use.

User-Facing Functions Are Not the Syscalls Themselves

A subtlety worth being precise about: fopen() in C, or open() in Python, are library functions, not syscalls. They live in Ring 3, do bookkeeping (buffering, error translation), and eventually issue the real, much lower-level syscall for you. On Windows the practical picture has an extra layer: application code usually calls the Win32 API (e.g. CreateFileW), which calls into ntdll.dll, which is what actually executes the syscall instruction down into the NT kernel. Knowing this distinction matters because tracing tools operate at different layers — a Win32 API monitor and a raw syscall tracer will show you related but not identical events.

Everything left of the diagonal line is Ring 3, no matter how "low-level" it looks. Only the final jump is the actual privilege transition.

You Can Watch This Boundary Happen

Windows ships Process Monitor (ProcMon), which hooks the OS's own tracing facilities to show you file, registry, and network operations per-process, timestamped, with the calling stack. Linux has strace, which attaches to a process via ptrace and prints every raw syscall with its arguments and return value. Module 3 has you run one of these against a trivial program and read real, captured syscall activity — not a description of what syscalls "generally" happen.

ProcMon's default view is enormous — every process on the system, every operation. If your capture looks empty or overwhelming, the fix is almost always the filter bar (Process Name is your program), not a broken installation.
