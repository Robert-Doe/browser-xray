IPC Across the Stack

Five modules, one family of mechanisms. This page is the side-by-side comparison no single module's own scope covers.

00Why This Is Centralized

Module 6 built pipes and sockets as raw OS primitives. Module 7 built shared memory as the deliberate exception to process isolation. Module 8 built a custom, application-level protocol on top of one of those primitives. Modules 15 and 16 pointed the identical socket mechanism at the real internet, using a real, standardized protocol (HTTP) instead of an invented one. Each module's own job was to prove ONE mechanism worked, correctly, in isolation. None of them was the right place to ask the more practical question every one of these modules quietly assumed an answer to: given a choice, which mechanism do you actually reach for, and why?

02The One Axis That Actually Matters: Trust

Every one of these mechanisms answers the same underlying question — "how does data cross a boundary?" — but the boundaries themselves have wildly different trust levels, and that's what actually drives the real choice, more than raw performance. Shared memory is only ever appropriate between two components that already trust each other completely, because it offers literally no message-boundary enforcement — whoever's on the other end can write anything, whenever, into memory you're also reading. HTTP over TLS sits at the opposite end: it exists specifically to communicate with parties you have NO inherent trust in at all, which is exactly why it comes wrapped in explicit authentication (the TLS handshake, Module 15) and an explicit, standardized wire format anyone can independently implement and verify (Module 16).

03Where Real Chromium Sits on This Spectrum

Real Chromium's Browser Process ↔ Renderer Process link (which Module 8's toy version models) uses Mojo, Chromium's own IPC system — deliberately built as MESSAGE PASSING, not shared memory, for exactly the trust-boundary reason above: the Renderer Process is the LEAST trusted component in the entire architecture (it's the one running attacker-influenced content), so the Browser Process deliberately avoids ever mapping its own memory into it. Where Chromium DOES use shared memory (some compositor/GPU buffer handoffs), it's specifically for large, high-throughput data being passed between components that are ALREADY within the same trust boundary — matching this cluster's central point precisely.
