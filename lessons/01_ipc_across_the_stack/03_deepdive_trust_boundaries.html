Trust Boundaries: Matching the Mechanism to Who's on the Other End

01The Question Every Choice Actually Answers

Before asking "which IPC mechanism is fastest," the question that actually determines correctness is: if the process on the other end of this channel were fully compromised right now, what's the worst thing that channel lets it do to me? This course's own modules answer that question very differently for each mechanism:

  • Shared memory (Module 7): the worst case is total — a compromised peer can write ANYTHING into memory you also read, with no boundary checking at all. This is only acceptable when the peer is already inside your own trust boundary.
  • A named pipe or raw socket (Module 6): a compromised peer can send you malformed or malicious MESSAGE CONTENT, but cannot directly touch your memory — whatever damage it does has to go through however your own code interprets the bytes it sends.
  • HTTP over TLS (Modules 15–16): built assuming the peer might be fully adversarial from the start — hence authentication (Module 15's certificate verification) and a rigorously specified, widely-scrutinized wire format (Module 16), rather than an ad hoc protocol only your own two components need to agree on.

02Site Isolation's Real Consequence for This Choice

Module 11 proved that OS process separation alone doesn't stop a determined, privileged peer from reaching across — real containment needed an actual privilege/trust difference (an integrity-level gap) layered on top. That finding applies DIRECTLY here: choosing shared memory between two components is only as safe as your actual confidence that neither one will ever become the "privileged reader, compromised writer" pairing Module 11 demonstrated breaking through. If there's any realistic path for one side of a shared memory link to become attacker-controlled, that link is a liability exactly matching Module 11's Part A result — not a hypothetical one.

03A Concrete Rule of Thumb

Draw the trust boundary FIRST, based on what each side actually is (your own code you fully control? A sandboxed, potentially attacker-influenced renderer? A completely external, arbitrary internet server?) — then let that answer dictate the mechanism, not the other way around. Picking a fast mechanism first and hoping the trust question works out is precisely how real, serious security bugs get introduced into IPC-heavy systems.
