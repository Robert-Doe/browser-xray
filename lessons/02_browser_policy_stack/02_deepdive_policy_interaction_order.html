DEEP DIVE · BROWSER POLICY STACK

The Exact Interaction Order, Worked Through

01The Scenario

A page at https://app.example.com runs a script that calls fetch("http://api.example.com/data") — deliberately picking a plain-HTTP, cross-origin (different host AND scheme) target, so every single policy in this cluster has a real chance to matter.

02Step by Step, in the Real Order

  1. HSTS check (Module 31), before anything is sent: if the browser has previously seen an HSTS record for api.example.com, the URL is rewritten to https://api.example.com/data right here — before any network activity at all. Assume, for this walkthrough, no such record exists, so the request genuinely goes out over plain HTTP.
  2. SameSite check (Module 29), as the request is constructed: since app.example.com and api.example.com are different hosts but the SAME registrable domain (example.com), this is a SAME-SITE request — every cookie for api.example.com is attached regardless of its SameSite value. (If the target had instead been a genuinely different site, this step would filter cookies by SameSite value and request context.)
  3. CORS preflight decision (Module 18): a plain fetch() with no custom headers and the GET method is a "simple" request — no preflight OPTIONS round trip happens. (A PUT or a custom header would have triggered one, exactly as Module 18 demonstrated.)
  4. The request is sent, in the clear, over HTTP — mixed content doesn't apply here as a REQUEST-blocking mechanism (Module 31's mixed-content handling governs SUBRESOURCES like <img>/<script> tags embedded in a page, not same-page fetch() calls, which have their own separate "cross-origin request" handling above).
  5. The response arrives. SOP check (Module 17): is api.example.com the same origin as app.example.com? No (different host). Does the response carry an Access-Control-Allow-Origin header matching https://app.example.com (Module 18's actual response-side check)? If yes, the script gets to read the body. If not, the fetch resolves, but reading the body throws.
  6. CSP check (Module 30) — only relevant if the response body were HTML containing scripts, which a JSON API response typically isn't. If it were, script execution from that content would separately be gated by app.example.com's OWN CSP policy, entirely independent of everything above.

03The Takeaway

Five checks, five different questions, five different moments — and in this one example, only two of them (SameSite, SOP) actually changed anything about the outcome, while the others were "checked but not the deciding factor" for this SPECIFIC request. That's normal and expected: most individual requests only really exercise one or two of these five policies meaningfully. The value of knowing all five is being able to correctly identify WHICH ones matter for any given real scenario, rather than reaching for the wrong one (or assuming one covers a gap it doesn't).
