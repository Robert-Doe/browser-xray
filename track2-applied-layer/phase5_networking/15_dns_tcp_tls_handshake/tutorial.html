dns_tcp_tls_handshake

Proves: "loading a URL" is a strict sequence of independently measurable, real costs — DNS, then TCP, then TLS — every one of which completes before a single byte resembling the actual requested page exists anywhere.

00Prerequisites

sockets (Module 6's mechanism, now over a real network) reading hex Module 8: toy_browser_shell

01The Big Analogy

Ordering a package from a company you've never dealt with before isn't one action. First you look up their actual street address (DNS). Then a courier physically confirms someone's home and able to receive the package before handing anything over — a real, two-way "yes, I'm here, are you there" exchange (TCP). Then, before any sensitive paperwork changes hands, both sides verify each other's identity and agree on a private way to talk — sealed envelopes, a shared code (TLS). Only after ALL of that does the actual thing you ordered — the reason for the whole errand — even begin to move. Every step before it was real, necessary work, and none of it was the package itself.

02What Happens, Step by Step

  1. socket.getaddrinfo() asks DNS to resolve example.com — a real query, a real answer, with real measured latency.
  2. socket.create_connection() performs a real TCP three-way handshake to one of the resolved IPs on port 443, receiving back a genuine OS-assigned local ephemeral port.
  3. ssl.create_default_context().wrap_socket() performs a real TLS handshake over that connection — real certificate validation, real cipher negotiation.
  4. Only now does a real HTTP HEAD request get sent, and only now does anything resembling "the response" exist.

04The Code, Explained

results = socket.getaddrinfo(hostname, PORT, proto=socket.IPPROTO_TCP)
...
sock = socket.create_connection((ip, PORT), timeout=10)
...
tls_sock = context.wrap_socket(sock, server_hostname=hostname)

Three separate function calls, three separate layers, three separate real network round trips (or, for DNS, often a cached local lookup — still a real query). Nothing here is a single "connect to a URL" black box — because there is no such single operation underneath; every browser performs exactly this same layered sequence, just usually hidden behind one address-bar Enter keypress.

07Brain Exercise

Step 3 confirms the server is genuinely "example.com," verified cryptographically. Does that verification tell you ANYTHING about whether the HTML that server eventually sends is safe, honest, or free of malicious script content? Think about what TLS actually checks before revealing the answer.
No — and this is a critical distinction to hold onto for the rest of this course. TLS verifies two things: that the data wasn't tampered with in transit (integrity), and that you're genuinely talking to the server that controls the private key matching this certificate for this domain (authentication). It says absolutely nothing about the CONTENT that server chooses to send you. A completely legitimate, correctly-TLS-verified server can still serve a page containing a stored XSS payload (Module 32), a malicious ad, or a compromised third-party script. "The padlock icon is green" has never meant "this page is safe" — it has only ever meant "you are talking to who you think you're talking to, privately." Confusing these two claims is one of the most common and consequential misunderstandings in practical web security.

08There Are No Dumb Questions

Why did DNS resolve to TWO different IP addresses?
Real production domains, especially ones behind a CDN like Cloudflare (visible in our captured certificate issuer), commonly resolve to multiple edge server IPs for load balancing and redundancy — this isn't unusual or a demo artifact, it's normal DNS behavior for any professionally-operated site.
Why does the local port change every time I run this?
It's an ephemeral port — the OS assigns one from a pool of available high-numbered ports for each new outbound connection, specifically so many simultaneous connections from the same machine don't collide. This is ordinary, expected TCP/IP stack behavior, the same underlying mechanism Module 6's socket demo used locally.
Is TLS 1.3 always what gets negotiated?
Not necessarily — it depends on what both the client (Python's OpenSSL-backed `ssl` module here) and the server support and prefer. An older server, or a client with an older TLS library, might negotiate TLS 1.2 instead. Seeing which version and cipher actually got chosen, rather than assuming, is exactly why this module reports it directly rather than asserting a fixed expectation.
What would change if I requested plain HTTP (port 80) instead?
Step 3 (the entire TLS handshake) would simply not happen — the HTTP request in Step 4 would go out as plain, unencrypted text immediately after the TCP handshake. That specific contrast — and why it matters — is exactly what Module 31 (mixed-content/HSTS) builds on directly.
