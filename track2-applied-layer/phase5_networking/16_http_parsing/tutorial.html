http_parsing

Proves: an HTTP response is plain, structured text over a socket — fully hand-parseable, including its two real body-framing mechanisms, with no library required.

00Prerequisites

Module 15: dns_tcp_tls_handshake reading raw bytes

01The Big Analogy

A telegram has a rigid, plain-text structure anyone can learn to read in five minutes: a line for the recipient, a blank line, the message body, and — critically — the sender always tells you either exactly how many words to expect, or marks the message in clearly delimited pieces if the total length wasn't known when sending began. There's no secret decoder ring. The entire "format" is a handful of plain-text conventions, agreed on in advance, followed consistently. An HTTP response is exactly this — the conventions just have specific names (status line, headers, Content-Length, chunked encoding).

02What Happens, Step by Step

  1. Raw bytes arrive over the socket (Module 15's channel).
  2. We find the first \r\n\r\n — that boundary separates the headers from the body, always, by spec.
  3. The first line before that boundary is the status line (HTTP/1.1 200 OK); every line after it is a Name: value header.
  4. We check ONE specific header, Transfer-Encoding, to decide how to read the body: if it says chunked, we reverse the chunk framing ourselves; otherwise, if Content-Length is present, we take exactly that many bytes; otherwise, whatever's left until the connection closes is the body.

04The Code, Explained

while True:
    line_end = chunked_body.index(b"\r\n", pos)
    size = int(chunked_body[pos:line_end].split(b";", 1)[0], 16)
    pos = line_end + 2
    if size == 0:
        break
    result.extend(chunked_body[pos : pos + size])
    pos += size + 2

Chunked encoding's whole idea: each piece of the body is preceded by its own length, written in hexadecimal, on its own line. Read the length, read that many bytes, skip the trailing \r\n, repeat — until a zero-length chunk says "that's everything." No external library logic is needed here; it's a length-prefixed framing scheme, the same underlying idea Module 8's IPC protocol used, just spelled out in hex text instead of raw binary bytes.

CAN'T DO YET

  • Parse HTML — this module stops at "here are the raw body bytes"; turning those bytes into a DOM starts at Module 19
  • Handle HTTP/2 or HTTP/3 framing — those use entirely different, binary framing schemes, not the plain-text HTTP/1.1 format this module parses

CAN DO NOW

  • Read any HTTP/1.1 response's raw bytes and know exactly where the body starts and how long it is
  • Explain why a server MUST specify one of two framing mechanisms (or close the connection) — without one, there is no way to know where the message ends
  • Recognize that "the server said Content-Length" is an assumption to VERIFY, not assume, for any specific real server

07Brain Exercise

Suppose a malicious server sent a response with BOTH a Content-Length header AND a Transfer-Encoding: chunked header, with conflicting framing information. Why might that specific ambiguity be dangerous in real systems, rather than just confusing? Think about what happens when TWO different systems (say, a proxy and the origin server) parse the SAME bytes differently, before revealing the answer.
This is a real, named, historically significant class of vulnerability called HTTP request/response smuggling. It's dangerous specifically because different systems in the same chain (a CDN or proxy, and the actual origin server) might resolve the Content-Length/Transfer-Encoding conflict DIFFERENTLY — one system decides the message ends at one point, the next system in the chain decides it ends somewhere else. That disagreement lets an attacker hide a second, smuggled request or response inside what the first system thought was the complete, single message — potentially reaching a victim (another user's request on a shared connection, or a security control the smuggled content bypasses) that was never supposed to see it. This module's parser doesn't defend against this — real-world guidance (per the HTTP specification) is that a compliant implementation should REJECT a message with both headers present rather than try to guess which one wins, precisely because that ambiguity itself is the vulnerability.

08There Are No Dumb Questions

Why does chunked encoding exist at all — why not always use Content-Length?
Content-Length requires knowing the total body size BEFORE you start sending it. That's easy for a static file, but often impossible for dynamically generated or streamed content (think: a live video feed, or a page generated progressively). Chunked encoding lets a server start sending data immediately, one known-size piece at a time, without ever needing to know the grand total in advance.
What happens if neither Content-Length nor chunked encoding is present?
Per HTTP/1.1's own rules, the body is understood to run until the connection closes — which is exactly the fallback branch this module's parser implements, and exactly why our fetch functions loop on recv() until it returns empty rather than reading a fixed amount.
Why lowercase every header name during parsing?
Because HTTP header names are explicitly case-insensitive by specification — a server is free to send Content-Length, and another to send content-length, and both are equally valid. Normalizing during parsing means code using this parser never has to remember to check every possible capitalization itself.
Is this parser something a real browser would actually use?
Conceptually, yes — every real browser's networking stack contains logic performing exactly these same checks (find the header/body boundary, check Transfer-Encoding, fall back to Content-Length, fall back to connection-close), just written in a systems language, heavily optimized, and hardened against malformed/adversarial input in ways this teaching-scoped parser deliberately doesn't attempt.
