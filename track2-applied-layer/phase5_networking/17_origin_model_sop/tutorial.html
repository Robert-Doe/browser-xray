TRACK 2 · PHASE 5 · MODULE 17 · THE MOST CONSEQUENTIAL RULE ON THE WEB

origin_model_sop

Proves: the browser — not the server, not the network — is what stops a script from origin A reading a response from origin B, and proves it by showing the network request happens identically in both the blocked and unblocked case.

00Prerequisites

the origin tuple Module 16: http_parsing Module 8: toy_browser_shell

01The Big Analogy

A courier genuinely delivers a sealed envelope to your desk — the delivery itself always happens, the courier's job is done, full stop. What happens next is entirely a decision made at YOUR desk: your office's own policy might say "don't open envelopes addressed to a different department," and if this envelope wasn't addressed to you, your office assistant intercepts it and refuses to let you read the contents — even though it's sitting right there, already delivered, already in the building. The courier company never knew or cared about any of this. The refusal was never about delivery. It was always about who's allowed to open what, decided entirely on your side of the transaction.

02What Happens, Step by Step

  1. Two toy origins run locally — different ports, so genuinely different origins by the strict definition (Prerequisite 8).
  2. naive_fetch() sends a real request to origin B and returns whatever comes back, with no awareness that "origin" is even a concept.
  3. sop_enforced_fetch() sends the exact same real request — the bytes leave the machine, origin B's server responds, exactly as before.
  4. Only after that real response is fully received does the wrapper check: does the requesting page's origin match the response's origin?
  5. If not, the response is real, complete, sitting in memory — and deliberately withheld from the caller.

03What We Actually Captured

=== Part A: naive_fetch -- NO origin check at all ===
  script on origin A read origin B's response directly: b'PRIVATE_SESSION_DATA_FOR_ORIGIN_B_ONLY'

=== Part B: sop_enforced_fetch -- cross-origin, from origin A to origin B ===
  BLOCKED, as expected: script running on http://127.0.0.1:51960 may not read
  a response from http://127.0.0.1:51961 -- request WAS sent and a real
  response WAS received over the network; the browser is withholding it
  from script, not preventing the request itself

=== Part C: sop_enforced_fetch -- SAME origin (A fetching from A) ===
  ALLOWED, as expected: b'public content from origin A'
Real, captured output. Same network layer, same servers — the only thing that changed between Part A and Part B was whether anything checked the origin before handing back the response.

04The Code, Explained

raw = _raw_get(target_url)  # the network request happens regardless
response = parse_response(raw)

if not same_origin(requesting_origin, target_origin):
    raise BlockedBySameOriginPolicy(...)

return response.body

Read the order of operations literally: the request is sent and the response is fully parsed before the origin check even runs. This isn't an accident of this toy implementation — it mirrors something genuinely true about real browsers: the network layer doesn't know or care about JavaScript's Same-Origin Policy. The policy is entirely about what the browser lets script code read afterward.

07Brain Exercise

Given that the request in Part B genuinely reached origin B's server and origin B genuinely processed it and sent back a real response — could origin B's server have been affected by that request (e.g. if it were a request that changed data, not just read it), even though the BROWSER blocked reading the response? Think it through before revealing the answer.
Yes — and this is exactly the gap that makes CSRF (Cross-Site Request Forgery) possible, which Module 32 demonstrates directly. SOP blocks a malicious page from reading the response of a cross-origin request. It does nothing to stop the request from being sent, and it does nothing to stop that request from having a real, permanent side effect on the server if the server itself doesn't separately verify the request's legitimacy (e.g. via a CSRF token). A malicious page can, for instance, cause your browser to send a real, cookie-authenticated "transfer money" or "change my email" request to a site you're logged into — SOP never promised to stop the request, only to stop the malicious page from reading what came back. This is precisely why "same-origin policy" and "protects you from all cross-origin attacks" are NOT the same claim, and conflating them is a common, consequential mistake.

08There Are No Dumb Questions

If SOP doesn't stop the request, what's the point of it?
It stops the single most dangerous consequence of a cross-origin request for a passive attacker: reading back sensitive data (your bank balance, your private messages, an API token) that a cookie-authenticated request to another site would return. That's an enormous, genuinely load-bearing protection — it's just not the same claim as "stops the request from happening," which is a separate concern (Module 32's territory).
Does 127.0.0.1:51960 and 127.0.0.1:51961 really count as "different origins" the way two real websites would?
Yes — by the strict origin definition (Prerequisite 8), port is a full, equal member of the comparison. Two services on the same machine, same IP, different ports are exactly as "different-origin" to a browser as two completely unrelated domains would be.
Would a real browser's fetch() behave exactly like this module's sop_enforced_fetch()?
Conceptually yes for the core behavior demonstrated here (block reading a cross-origin response by default) — though real browsers layer additional nuance on top (some cross-origin responses are partially readable in limited "opaque" forms, and CORS headers can change the outcome entirely, which Module 18 covers). This module isolates the DEFAULT, no-CORS behavior specifically.
Why compare origins as a plain 3-tuple instead of, say, a formatted string comparison?
A tuple comparison makes every part of the check explicit and equally weighted in one visible line — a string-based comparison risks subtle bugs (e.g. accidentally normalizing case differently per field, or a formatting difference that makes two equal origins compare unequal as strings). Precision here matters enormously, since this exact check is the entire security boundary.
