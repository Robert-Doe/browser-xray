cors_preflight

Proves: CORS is a server-controlled, per-origin, opt-in relaxation of the Same-Origin Policy default — enacted through a real extra round trip specifically so the browser can ask permission before a risky request, not just check permission after.

00Prerequisites

Module 17: origin_model_sop Module 16: http_parsing

01The Big Analogy

Module 17's courier always delivers, no matter what. CORS adds a phone call BEFORE certain deliveries — specifically the kind that could change something at the destination (a signed-for package, not a simple flyer). "Hello, this is a courier calling on behalf of Building A. Are you expecting a delivery from Building A, and are you willing to accept a package matching this description?" Only if the answer is a clear, specific "yes, from Building A, specifically that kind of package" does the courier actually complete the real delivery. The phone call isn't paranoia for its own sake — it exists specifically because some deliveries do things you can't cleanly undo once they've arrived.

02What Happens, Step by Step

  1. A cross-origin, non-simple request (a PUT with a custom header) is about to be made.
  2. Before sending it for real, the browser sends an OPTIONS preflight, declaring the method and headers it intends to use, and its own origin.
  3. The server checks its own policy and responds — with Access-Control-Allow-* headers if it grants permission, or without them if it doesn't.
  4. Only if the preflight response explicitly grants this exact origin and method does the browser send the real request.
  5. Even then, the REAL response must ALSO carry a matching Access-Control-Allow-Origin header before the browser will expose its body to script.

04The Code, Explained

if _needs_preflight(method, custom_headers):
    status, headers, _ = _raw_request(target_url, "OPTIONS", preflight_headers)
    allow_origin = headers.get("access-control-allow-origin")
    allow_methods = headers.get("access-control-allow-methods", "")
    if allow_origin != str(requesting_origin) or method not in allow_methods:
        raise BlockedByCORS(...)
# only reached if the preflight was explicitly granted:
_, headers, body = _raw_request(target_url, method, actual_headers)
if headers.get("access-control-allow-origin") != str(requesting_origin):
    raise BlockedByCORS(...)

Two separate checks, two separate real network round trips. The preflight decides whether the real request gets sent AT ALL. The second check — on the real response — is the part that's easy to forget: a browser doesn't just trust a prior preflight grant forever; it checks the actual response too.

07Brain Exercise

Why does the real CORS spec require a SEPARATE preflight round trip for a `PUT` request, instead of just sending the `PUT` immediately and checking `Access-Control-Allow-Origin` on the response the same way a simple `GET` does? Think about what a `PUT` might already have DONE by the time any response comes back, before revealing the answer.
Because by the time a response comes back, it's often too late — a `PUT` (or `DELETE`, or a `POST` with a non-form content type) can already have changed data on the server the moment it arrived, regardless of what the response says afterward. A `GET` is assumed "safe" in the sense that merely making the request doesn't change server state, so checking permission after-the-fact (on the response) is an acceptable risk — worst case, a script read something it shouldn't have, which Module 17's blocking already prevents. A `PUT` needs permission BEFORE the request is sent at all, precisely because the browser cannot un-ring that bell once the server has acted on it. This is exactly why "simple" methods skip preflight and "non-simple" ones don't — the line is drawn based on which requests can have an effect the response-side check comes too late to prevent.

08There Are No Dumb Questions

Could a malicious server pretend to grant CORS to everyone with a wildcard `*`?
Yes, and many legitimate public APIs genuinely do this deliberately, when the API's data is meant to be freely cross-origin accessible (a public weather API, for instance). The server is always the one deciding its own policy — CORS gives servers a real, deliberate way to opt in to being cross-origin readable, precisely because sometimes that's exactly what's wanted.
Does the preflight request carry the actual data being sent (e.g. the PUT's body)?
No — the preflight is deliberately lightweight: just the intended method and headers, asked about in advance. The actual body is only sent with the real request, after permission is confirmed.
What happens to a "simple" GET request cross-origin — does it skip ALL checking?
No — it skips the PREFLIGHT specifically, but the response-side check (does the response carry a matching `Access-Control-Allow-Origin`?) still applies, exactly as Module 17 demonstrated for the no-CORS default case. "Skips preflight" and "skips all CORS checking" are not the same thing.
Is CORS a security mechanism protecting the SERVER, or the BROWSER's user?
Primarily the user (and, transitively, the origin whose data might otherwise leak) — CORS exists so a browser knows whether it's safe to expose a cross-origin response to a potentially untrusted script. It's not primarily there to protect the server from receiving requests; Module 17's lesson (the request still happens) applies here too.
