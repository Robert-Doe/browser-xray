00Prerequisites

Module 16: http_parsing

01The Big Analogy

A postal sorting machine reads addresses letter by letter, always knowing exactly what "mode" it's in: reading a street number, reading a street name, reading a ZIP code. It never "looks ahead" or guesses the whole address at once — it transitions between a small set of known modes, one character at a time, and every mode has an exact, predefined rule for what happens next, INCLUDING what happens when the writing is smudged, misspelled, or doesn't quite match the expected format. Nothing about a smudge crashes the machine — there's a defined "best effort" behavior for every smudge type the machine's designers anticipated. HTML tokenization is exactly this kind of machine, and the "smudges" — malformed markup — have exact, specified outcomes, not undefined behavior.

02What Happens, Step by Step

  1. The tokenizer starts in the DATA state, reading plain text one character at a time.
  2. Hitting < transitions to TAG_OPEN — but only a letter after it commits to actually being a tag; a space, digit, or anything else means "false alarm," and the < goes right back into the text as a literal character.
  3. A real tag walks through TAG_NAME, BEFORE_ATTRIBUTE_NAME, ATTRIBUTE_NAME, and value states, character by character, each state knowing exactly what ends it and what state comes next.
  4. Malformed sequences (<?xml...?>, an invalid end-tag name) are routed to BOGUS_COMMENT — a real, specified fallback, not a crash.
  5. At every point, whatever plain text has accumulated is only added to the token stream once something else is about to be emitted — never before, never out of order.

04The Code, Explained

def _emit(self, token) -> None:
    self._flush_char_buffer()
    self.tokens.append(token)

This one small method is the fix for a real bug we hit while building this module: an earlier version scattered manual "flush the pending text" calls across several state transitions, and missed one — producing a token stream where text appeared after a comment it should have preceded. Routing every non-character token through this single method makes that class of bug structurally impossible: there is no longer a second place to remember to flush.

07Brain Exercise

Two different browsers, both fully spec-compliant, are given the exact same malformed HTML. Should you expect them to ever tokenize it differently? Think about what "spec-compliant" actually guarantees, before revealing the answer.
No — and this is precisely why the HTML5 tokenization algorithm was written as an exhaustive, exact state machine (unlike earlier, looser "HTML" specifications that left error recovery implementation-defined). Before HTML5, different browsers genuinely DID recover from malformed markup differently, which was a real, practical, and sometimes security-relevant problem — a page could look different, or a security filter could parse content differently than the browser ultimately rendering it, exactly the same class of ambiguity as HTTP request smuggling (Module 16). HTML5's fully-specified tokenizer algorithm — the one this module implements a real subset of — exists specifically to guarantee that two compliant implementations handle every malformed case identically, closing off an entire class of cross-browser inconsistency and parsing-differential vulnerability.

08There Are No Dumb Questions

Why does `` become a comment instead of being recognized as an XML declaration?
Because HTML is not XML, and the HTML5 tokenizer has no special handling for XML processing-instruction syntax at all — anything starting `
Why does an unclosed tag at EOF not raise an error?
Because real-world HTML on the actual web is full of small errors, truncated responses, and imperfect markup — and browsers are specified to degrade gracefully rather than refuse to render a page over a missing closing tag. "Be liberal in what you accept" is a deliberate, spec-level design philosophy for HTML specifically.
Is a hand-rolled tokenizer like this ever used in production software, or is it purely educational?
Real production HTML parsers (browser engines, and standalone libraries like Python's own `html.parser`) are built on exactly this state-machine shape — this module's tokenizer is a genuine, scoped implementation of the same approach, not a toy simplification of a fundamentally different real technique.
What's the difference between a "parse error" in this spec and an error in most programming languages?
In most languages, an error typically stops execution or throws an exception. In the HTML5 tokenization spec, a "parse error" is just a label for "this is malformed input" — it's paired with an exact, specified recovery action, and processing always continues. The term describes non-conformance in the input, not a failure in the tokenizer.
