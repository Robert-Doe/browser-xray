01The Big Analogy

A building's structural blueprint (which rooms exist, how they connect) and its interior design plan (paint colors, furniture placement) are drawn by different people, on different documents, using different notations — and crucially, the design plan can be completely and correctly finished without either document ever referencing the other by name during drafting. Only much later does someone hold both documents side by side and say "this color goes in that room." The CSSOM is the design plan: parsed to completion, entirely on its own terms, with no awareness whatsoever of any specific HTML document it might eventually be paired with.

02What Happens, Step by Step

  1. Comments are stripped in one pass, since they can appear almost anywhere and never nest.
  2. The parser reads characters up to the next {, treating that as raw selector text — split on commas into a list.
  3. Inside the braces, each declaration is read up to the next ; or } — but characters inside a quoted string are never treated as that boundary, even if they're literally a semicolon or brace.
  4. Each declaration is split on its first : into a property and a value; a trailing !important (with or without a space) is detected and stripped off separately.
  5. A declaration with no colon at all is discarded — and parsing simply continues with whatever comes next.

03What We Actually Captured

=== a string value containing ';', '{', '}' as literal text, not syntax ===
input: 'p::before { content: "a;b{c}"; color: red; }'
p::before {
    content: "a;b{c}";
    color: red;
}

=== a malformed declaration in the middle -- real CSS error recovery ===
input: 'div { color: red; this is garbage; font-size: 12px; }'
div {
    color: red;
    font-size: 12px;
}
(recovered from malformed declaration(s): ['this is garbage'])

=== an @media block skipped as a balanced unit, without breaking later rules ===
input: '@media (max-width: 600px) { p { color: green; } } div { color: red; }'
div {
    color: red;
}
Real, captured output. Every genuinely tricky case — embedded syntax characters in a string, a broken declaration, an entire unparsed at-rule block — recovered exactly as real CSS specifies.

04The Code, Explained

if in_string:
    buf.append(c)
    if c == in_string:
        in_string = None
    self.pos += 1
    continue
if c in ('"', "'"):
    in_string = c
    ...

This is the one piece of state (in_string) that makes the whole parser grammar-correct rather than a naive split. Without it, content: "a;b{c}"; would be sliced apart at the semicolon and brace INSIDE the quotes — a real, easy mistake a regex-based approach makes constantly.

07Brain Exercise

This module deliberately skips `@media` blocks without parsing their contents. What real, practical capability does a browser lose if its CSS engine ONLY ever did this — skip every `@media` block completely, forever? Think about what `@media` is actually for before revealing the answer.
Responsive design — an engine that always skips `@media` blocks would render every page as if no responsive breakpoints existed at all, always applying only the "base" styles regardless of screen size, zoom level, print context, or any other media condition. `@media` is exactly how a stylesheet says "these rules only apply under these conditions" — skipping it entirely doesn't break parsing (which is why safe-skipping is the right behavior for THIS module's narrower goal), but a real browser has to go much further: parse the media query condition itself, evaluate it against the actual current viewport/device, and only THEN decide whether to apply the rules inside. This module proves the "don't break on what you don't understand yet" half of the story; a real engine's `@media` support is the "and here's how we actually understand it" half, deliberately left for you to research further, since it's a substantial feature of its own.

08There Are No Dumb Questions

Why does CSS recover from errors so much more gracefully than, say, JSON or a programming language?
Deliberate design choice by CSS's original authors, specifically because stylesheets are meant to keep working across old and new browsers, and across typos, without one small mistake taking down an entire page's appearance. A JSON parser failing on one bad comma is a reasonable design for a data-interchange format; a CSS engine failing on one bad declaration would be a poor experience for a presentation layer meant to degrade gracefully.
Is `!important` a hack, or a real, intentional CSS feature?
Completely real and intentional — it's part of how the CSS cascade resolves conflicting rules, letting a specific declaration override rules that would otherwise win based on specificity or source order. Module 22 builds the cascade logic `!important` actually plugs into.
Why split selectors on commas here, if we're not parsing them fully yet?
Because "these declarations apply to ALL of these selectors" is part of the CSSOM's actual structure, independent of what any one selector string means — `h1, h2 { margin: 0; }` is genuinely one rule with two selectors sharing declarations, not two separate rules, and the CSSOM needs to preserve that grouping even before Module 22 gives the selector text itself any meaning.
What would happen if a declaration's value itself contained an unclosed string, like `content: "oops;`?
The parser would keep consuming everything after that point — including what you intended as subsequent rules — looking for the matching closing quote, since it correctly (per real CSS grammar) treats everything inside an open string as literal text. This matches real CSS behavior; an unterminated string is a genuinely serious error in real stylesheets too, not just in this module's implementation.
