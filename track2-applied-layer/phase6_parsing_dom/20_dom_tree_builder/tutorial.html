01The Big Analogy

A single elevator serves an office building, and at any moment, it's only ever "at" one specific floor — that's where anyone getting in right now will end up. Someone pressing a button for Floor 2 doesn't need to know or care that a moment ago the elevator was on Floor 5, or how it got down to 2 — all that matters is where it is right now. A stack of open elements works exactly like that elevator's current floor: at every moment during parsing, there's exactly one "current" node new content gets inserted into, and specific, simple rules govern when the elevator moves — some of them surprisingly, like automatically heading back down a floor the instant certain buttons get pressed, whether or not anyone asked for that in so many words.

02What Happens, Step by Step

  1. A stack starts with just the document at the bottom.
  2. A StartTag token creates a new element, appends it as a child of whatever's currently on TOP of the stack, then pushes itself onto the stack (becoming the new "current" insertion point) — unless it's a void element like <img>, which can never contain anything, so it's never pushed.
  3. Before that push, one specific check runs: is the CURRENT top of the stack a <p> and the new tag is ALSO <p>? If so, pop the old one first — the real, famous auto-close rule.
  4. An EndTag token scans down the stack for a matching element, and — if found — removes it AND everything still open above it.
  5. Character and Comment tokens simply attach as children of whatever's currently on top.

04The Code, Explained

top = stack[-1]
if isinstance(top, Element) and top.tag in AUTO_CLOSE_ON_OPEN.get(token.name, ()):
    stack.pop()  # the real, observable "auto-close" behavior

element = Element(tag=token.name, attributes=dict(token.attributes))
current().children.append(element)
if token.name not in VOID_ELEMENTS and not token.self_closing:
    stack.append(element)

"Browsers are forgiving about unclosed <p> tags" is usually stated as a vague fact. Here it's four lines: check the top of a stack, maybe pop it, append a child, maybe push. Nothing about it is a special case bolted onto an otherwise-strict parser — it's the SAME mechanism every single element uses to get inserted at all.

08There Are No Dumb Questions

Why is it called a "stack of open elements" specifically?
Because it behaves exactly like the data structure of that name: elements are pushed on top when opened, popped off the top (or from wherever a match is found, removing everything above it too) when closed, and the top of the stack is always "where we currently are" in the tree — first-in-last-out ordering, the defining property of a stack.

    Why does a void element like `` still get appended to the tree, if it's never pushed onto the stack?
    Because it's still a real node in the tree — a `` element exists and has attributes (like `src`) even though nothing can be "inside" it. Not pushing it only means the NEXT piece of content won't be mistakenly nested inside it — the element itself is unaffected.
    Is this module's tree the same shape a real browser's DevTools "Elements" panel would show for the same HTML?
    For every case this module actually tests, yes — the shapes shown here match real browser behavior. For deeper edge cases involving the full scope algorithm or the adoption agency algorithm (see the Brain Exercise), a real browser's tree could differ from this module's simplified version.
