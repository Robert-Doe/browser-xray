cookies_samesite

Proves: SameSite is a browser-enforced boundary based on registrable domain ("site," not exact origin) — and that its real rules depend on BOTH cross-site status AND request context (top-level navigation vs. subresource, safe vs. unsafe method) together, not a single simplified axis.

00Prerequisites

same-origin vs. same-site Module 17: origin_model_sop

01The Big Analogy

A family owns several storefronts across town, all under the same registered business name — a bakery, a café, a catering office — each a different building, but unmistakably "the same outfit" to anyone checking business records. A courier delivering BETWEEN those storefronts is trusted more loosely than one arriving from a complete stranger's shop across the street, even if the stranger's shop happens to be right next door. "Same business" (same-site) is a coarser, business-registry-level check than "exact same building" (same-origin) — and crucially, how much a delivery is trusted also depends on HOW it arrives: someone walking in the front door in person (a top-level navigation) is treated differently than a parcel slipped through a mail slot from outside (a background subresource request), even from the identical outside sender.

02What Happens, Step by Step

  1. A cookie is set with a SameSite value: Strict, Lax, or None.
  2. When a request is about to be sent, the browser computes the REGISTRABLE DOMAIN of both the requesting page and the target — using a Public Suffix List to correctly handle multi-label suffixes like .co.uk.
  3. If they match (same-site), every cookie for the target is attached, regardless of its SameSite value.
  4. If they don't match (cross-site), the decision gets more specific: None cookies always go; Strict cookies never go; Lax cookies go ONLY if this is a top-level navigation using a safe method (GET/HEAD) — never for a background subresource request, and never for an unsafe method like POST, even from a top-level navigation.

Notice Lax requires TWO conditions joined with and — top-level navigation AND a safe method. Losing either one changes the outcome, exactly as the captured output's last two rows show: dropping "top-level" (subresource request) or dropping "safe method" (POST) both independently cause the Lax cookie to be withheld.

07Brain Exercise

Given everything this module just proved, would a `SameSite=Lax` cookie be sent along with a cross-site image tag (`<img src="https://bank.example.com/logo.png">`) embedded on `evil.com`'s page? Reason through which category that request falls into before revealing the answer.
No — an `` tag's request is a SUBRESOURCE request (the browser fetching an image to display within `evil.com`'s own page), not a top-level navigation (the user's address bar actually going to `bank.example.com`). This module's own captured "Cross-site SUBRESOURCE/XHR request" row shows exactly this case: only the `None` cookie is attached; `Lax` is withheld. This is a real, deliberate part of why `SameSite=Lax` (the real browser DEFAULT for cookies that don't specify a value at all, in modern browsers) meaningfully reduces cross-site cookie leakage risk for embedded resources like images, scripts, and iframes, while still allowing a cookie to work normally when a user directly clicks a link or types a URL that lands on the site.

08There Are No Dumb Questions

Is "same-site" the same thing as "same-origin"?
No — this is one of the most commonly conflated pairs in web security. Same-origin (Module 17) requires scheme, host, AND port to match exactly. Same-site only compares the registrable domain — `https://a.example.com` and `https://b.example.com` are NOT same-origin (different hosts) but ARE same-site (same registrable domain, `example.com`).
Why does `SameSite=None` require `Secure`?
Because a cookie marked `None` is telling the browser "send me on every cross-site request, no restriction" — if that were also allowed over plain HTTP, the cookie could be trivially intercepted by anyone on the network path. Requiring `Secure` (HTTPS-only) alongside `None` is a real, deliberate browser safeguard against exactly that.
Why is `co.uk` a tricky case for computing a registrable domain?
Because a naive "take the last two labels" approach would treat `example.co.uk` as though `co.uk` were the registrable part and `example` were a subdomain of it — but `co.uk` isn't independently registrable; `example.co.uk` (three labels) is the actual registrable domain. Getting this wrong would incorrectly treat `bank.co.uk` and `evil.co.uk` as "same-site" just because they share a `.co.uk` suffix, which is precisely the kind of mistake a real Public Suffix List exists to prevent.
Does the SERVER or the BROWSER decide whether a cookie gets attached?
The server only ever DECLARES a cookie's SameSite value when setting it. Every single enforcement decision at REQUEST time — checking same-site status, navigation type, and method — happens entirely in the browser, the same "browser enforces, not the server" pattern Module 17 established for the Same-Origin Policy.
