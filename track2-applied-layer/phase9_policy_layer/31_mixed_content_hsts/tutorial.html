TRACK 2 · PHASE 9 · MODULE 31 · PHASE FINALE

mixed_content_hsts

Proves: HSTS and mixed-content handling both exist to prevent a silent, attacker-exploitable downgrade from HTTPS to HTTP — one by rewriting requests before they're sent, the other by treating different resource types by real, differing risk.

00Prerequisites

Module 30: csp_enforcement Module 15: dns_tcp_tls_handshake

01The Big Analogy

Imagine a courier service that, the very first time you use them, hands you a permanent note: "from now on, always call our SECURE line — never the old public one, even if someone tells you to." From that point forward, you don't even dial the old number to be redirected — you never dial it at all, because dialing it even once means whoever's tapped that old line already has what they wanted before your call ever reaches the courier. HSTS is that permanent note. Once received, the insecure line is never touched again, not even for a single ring.

02What Happens, Step by Step

  1. A site's HTTPS response includes Strict-Transport-Security: max-age=31536000; includeSubDomains — recorded by the browser.
  2. Any FUTURE request to that host (or a subdomain, since includeSubDomains was set) starting with http:// is rewritten to https:// — before the browser makes any network call at all.
  3. Separately, on an already-HTTPS page, a subresource request that's still plain HTTP gets checked: is it passive content (image, audio, video)? Auto-upgrade to HTTPS. Is it active content (script, stylesheet, frame)? Block it outright.

03What We Actually Captured

=== HSTS ===
  requested: http://example.com/login
  actually sent: https://example.com/login (upgraded)

  requested: http://sub.example.com/page
  actually sent: https://sub.example.com/page (upgraded)

  requested: http://not-example.com/page
  actually sent: http://not-example.com/page (unchanged)
