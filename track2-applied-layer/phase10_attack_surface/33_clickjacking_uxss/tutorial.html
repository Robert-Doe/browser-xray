01The Big Analogy

Clickjacking is like a prankster placing a perfectly clear pane of glass with an invisible "sign here" button exactly over a vending machine's visible "get a free sample" button — you press what you see, but the mechanism underneath the glass is what actually receives your finger's pressure, not what your eyes are looking at. UXSS is an entirely different kind of failure: not a trick played on your eyes at all, but a genuine flaw in the vending machine's own internal wiring that lets ANY customer's coin slot secretly open a completely different customer's locked compartment — a flaw in the machine itself, regardless of which specific customers happen to be using it.

02What Happens, Step by Step

  1. Clickjacking: two layers occupy the exact same screen coordinates — a visible one from origin A, a nearly-invisible one from origin B, with origin B's layer on top (higher z-index).
  2. A click at that coordinate is resolved by hit-testing: highest z-index wins, opacity is never consulted.
  3. The user perceives clicking origin A's visible button; the click actually reaches origin B's invisible one.
  4. The real defense (frame-ancestors) works differently: origin B's page simply refuses to be embedded in a frame AT ALL — checked before any framing succeeds.
  5. UXSS: a browser engine function that's supposed to check origin before returning cross-window data has that check disabled (modeling a real engine bug).
  6. A script from a completely unrelated origin calls that function and receives another origin's real document content directly.

04The Code, Explained

candidates = [l for l in layers if point_in_bounds(l, x, y)]
return max(candidates, key=lambda layer: layer.z_index)  # opacity never checked

That missing opacity check isn't a bug — real compositors genuinely don't consult it for hit-testing, because doing so would break entirely legitimate fade-in animations and semi-transparent interactive overlays. Clickjacking exploits a real, correct design decision, not a flaw in it.

07Brain Exercise

Given that UXSS is a bug in the BROWSER ENGINE itself, not any individual website, would Module 32's CSP defense (script-src, no unsafe-inline) have stopped this module's UXSS demonstration? Think about WHERE in the process each defense actually operates before revealing the answer.
No — and this is the single most important distinction this module draws. CSP is a policy the WEBSITE declares, enforced by a CORRECTLY-FUNCTIONING browser engine that checks it. UXSS, by definition, is a bug in that enforcement machinery itself — if the engine's own origin-checking code has a flaw, no amount of correct CSP configuration on the victim's part changes anything, because the bug lives one layer BELOW where CSP operates. This is exactly why real UXSS vulnerabilities are considered so severe: they can't be defended against by any individual website's own configuration at all — the only real fix is a browser engine patch, which is also why these bugs, when found, are typically reported directly to browser vendors (as critical security bugs) rather than being something a website operator could mitigate on their own end.

08There Are No Dumb Questions

Why doesn't the browser just check opacity and refuse clicks on nearly-invisible elements?
Because that would break real, legitimate UI patterns — a button fading in over 300ms, or a semi-transparent modal that's genuinely meant to be clickable while partially see-through. There's no opacity threshold that reliably distinguishes "legitimate low-opacity UI" from "malicious invisible overlay" without breaking real use cases, which is exactly why the real defense (`frame-ancestors`) works at a completely different layer — preventing the embedding itself, not trying to police opacity.
Is `X-Frame-Options` the same thing as `frame-ancestors`?
Closely related — `X-Frame-Options` (an older header, values like `DENY` or `SAMEORIGIN`) was the original clickjacking defense; `frame-ancestors` (a CSP directive) is its modern, more flexible successor, supporting a list of specific allowed embedding origins rather than just deny-all or same-origin-only. Real sites often send both, for compatibility with older browsers.
Could UXSS and clickjacking ever combine in one real attack?
In principle, yes — they exploit entirely independent mechanisms, so nothing prevents a sufficiently motivated real attack from using both if both gaps happened to exist simultaneously. This module demonstrates each in isolation specifically to keep their genuinely separate root causes clear.
Why is the UXSS demo's "engine bug" just a boolean flag instead of something more realistic?
Precisely to isolate the CONSEQUENCE of a missing origin check from the specific, often highly technical mechanism a real bug might use to bypass it (a parsing edge case, a race condition, an incorrectly cached security decision). This module's job is proving what happens once such a check is missing, not cataloging every real way one could historically go missing.
