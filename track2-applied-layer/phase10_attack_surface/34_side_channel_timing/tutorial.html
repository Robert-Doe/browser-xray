TRACK 2 · PHASE 10 · MODULE 34

side_channel_timing

Proves: a real, measurable timing side-channel can recover secret data even when the Same-Origin Policy and site isolation correctly block every direct read — because neither policy was ever designed to hide how LONG something takes, only what it CONTAINS.

00Prerequisites

Module 17: origin_model_sop Module 11: site_isolation_model Module 12: aslr_and_leaks

01The Big Analogy

A locked vault's door is genuinely, completely opaque — you cannot see the combination through it, no matter how you try. But you CAN time how long the mechanism takes to reject a wrong combination. If a real mechanical lock's internal wheels click into place one at a time, correct-so-far, and the whole mechanism only jams and stops turning at the FIRST wrong wheel, someone patiently timing each attempt can learn the combination one digit at a time — never once seeing inside the vault, never touching a single tumbler directly. The vault's opacity was real and total. It just was never the only thing that mattered.

02What Happens, Step by Step

  1. A toy server verifies a secret token using a comparison that exits the INSTANT it finds a mismatched character.
  2. An attacker script — genuinely, correctly blocked by SOP from ever reading the server's response content — instead just measures how LONG each guess takes to be rejected.
  3. A guess with more correct leading characters takes measurably longer, because the comparison got further before exiting.
  4. Trying every possible character at each position, keeping whichever took longest, recovers the secret one character at a time — using nothing but timing.
  5. Switching the server to a constant-time comparison — one that always does the same work regardless of correctness — removes the signal entirely.

03What We Actually Captured

api.example.com's real secret token (never sent to the attacker directly): 'X7f9Qz2A'

=== BEFORE: api.example.com uses a non-constant-time comparison ===
  Attacker recovered, via timing alone: 'X7f9Qz2A'
  Matches the real secret? True

=== AFTER: api.example.com switches to a constant-time comparison ===
  Attacker recovered, via the IDENTICAL timing attack: 'beoMbBIu'
  Matches the real secret? False
Real, captured output. Identical attacker, identical technique, identical number of guesses — the secret's own comparison function was the only thing that changed.

04The Code, Explained

def naive_compare(guess, secret):
    for i in range(len(secret)):
        if guess[i] != secret[i]:
            return False   # <- exits HERE, having done LESS work for a wrong guess
        time.sleep(PER_CHARACTER_DELAY)
    return True

That single early return False is the entire vulnerability. It's not a contrived, artificial flaw — it's the natural, obvious way most programmers write a string comparison, which is exactly why non-constant-time comparison bugs are a real, recurring category of vulnerability in actual production code.

07Brain Exercise

This module's attack needed the attacker to make MANY repeated, timed guesses against the same secret. In a real browser talking to a real server over a real network, what makes this attack dramatically HARDER than this module's clean, in-process demo — and what does a real attacker typically do to compensate? Think about what sits between "the server's real processing time" and "what the attacker actually measures," before revealing the answer.
Real network jitter — variable, unpredictable delay from network routing, congestion, the operating system's own scheduling on both ends — adds noise far larger than this module's clean, local, microsecond-scale signal. A real-world timing attack over a network compensates the same way this module's own `_time_guess()` does, just at a much larger scale: take MANY repeated measurements of the same guess and use a statistical technique (like the minimum, or a more sophisticated statistical estimator) to filter out noise and recover the smaller, real underlying signal. This is precisely why real, practical network-based timing attacks (several of which are real, published, and were used against real systems historically) often require thousands or millions of requests to reliably extract even a modest amount of secret information — the underlying vulnerability is identical to what this module demonstrates; only the amount of statistical averaging needed to see it clearly differs.

08There Are No Dumb Questions

Why does the "AFTER" attack still run for a while, if it can't recover anything?
Because the ATTACK ITSELF doesn't know in advance that it will fail — it still tries every candidate character at every position and measures timing, exactly as before. The difference is that those measurements no longer correlate with correctness at all, so the "best" (longest-timed) guess at each position is effectively random noise, not a real signal.
Is `hmac.compare_digest` (Python's real, built-in constant-time comparison) doing something fundamentally different from this module's `constant_time_compare`?
Conceptually the same core idea (no early exit, uniform work regardless of where a mismatch occurs) — Python's real implementation is more carefully hardened at a lower level (partly implemented in C, specifically to resist compiler optimizations that could reintroduce timing variance) than this module's illustrative Python version, but the defensive PRINCIPLE is identical.
Does adding `time.sleep()` make MY code vulnerable, or was it just needed to make this demo reliably measurable?
Purely a demo necessity — see `DECISIONS.md`. The real vulnerability is the EARLY EXIT (`return False` at the first mismatch), not the presence of a delay. Real vulnerable code doesn't need an artificial sleep at all; the natural cost of doing "more work" (comparing more characters) before exiting is already enough of a signal in real systems, especially over many repeated, statistically-averaged measurements.
Could this same class of bug exist in a JWT/API-key check, not just a plain string secret?
Yes, and this is a real, well-documented pattern — non-constant-time comparison bugs have been found historically in real authentication code checking API keys, HMAC signatures, and session tokens. It's exactly why security-conscious cryptographic and authentication libraries go out of their way to provide (and developers are strongly encouraged to use) dedicated constant-time comparison functions rather than a language's default `==`.
