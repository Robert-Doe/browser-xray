01The Big Analogy

A bank vault room has a locked door AND a guard who checks photo ID AND a camera system AND a silent alarm wired to the police. Ask "which one of these is the REAL security?" and the honest answer is: none of them, alone. A thief who defeats the lock still has to get past the guard. A thief who somehow gets past the guard is still on camera and still trips the alarm. Real vault security was never any single measure — it was the fact that defeating ALL of them, together, is a dramatically harder problem than defeating any one. This course's entire final module is that same observation, proven directly: two real locks, tested together and separately, on the exact same door.

02What Happens, Step by Step

  1. A "compromised renderer" probe — ordinary, unprivileged code, standing in for what an attacker's code would do after a REAL memory-safety bug (Module 14) gave them execution — attempts two things: spawn a new process, and tamper with a file.
  2. The identical probe runs four times, under four real combinations of Module 10's Job Object restriction and Module 9's least-privilege token.
  3. With neither active, both actions succeed — a full compromise.
  4. With only ONE active, that one specific action is blocked — but the other succeeds completely.
  5. Only with BOTH active are both actions blocked.

07Brain Exercise

This course built exactly two Track-1 sandboxing mechanisms (Modules 9 and 10) and combined them here. A real browser adds MORE layers still (AppContainer, more granular syscall filtering, GPU process isolation, and others). Given what Scenario D already showed — that combining just two independent, LIMITED mechanisms closed both gaps this module tested — what would you predict happens to an attacker's realistic chances as a real system adds even MORE independent layers, each with its own limited scope? Think about how independent probabilities combine before revealing the answer.
Each additional, genuinely independent layer that must ALSO be defeated multiplies the difficulty, not merely adds to it — if bypassing each individual layer requires its own separate, unrelated bug (as Modules 9 and 10's mechanisms did here: a token bug doesn't help you bypass a Job Object, and vice versa), an attacker needs a combination of independent bugs, not just one bigger one. This is precisely why modern browser sandbox escapes are typically reported as CHAINS of multiple distinct vulnerabilities (a renderer memory-corruption bug, PLUS a separate sandbox-escape bug, sometimes plus a kernel privilege-escalation bug on top) rather than a single flaw — real security researchers and browser vendors both think about sandbox strength in exactly these terms: not "is there a bug," but "how many independent bugs, in how many independent mechanisms, would someone need simultaneously." This module's four-scenario matrix is a small, concrete, directly-observed instance of that same, larger, real principle.

08There Are No Dumb Questions

Why didn't this module build a THIRD, brand-new sandboxing mechanism to add to the mix?
Because the point wasn't "more mechanisms are better" in the abstract — it was proving, with real evidence, that COMBINING already-independently-verified mechanisms produces a qualitatively different (much stronger) result than either alone. Two real, already-proven-real mechanisms were sufficient to demonstrate that precisely; a third would add complexity without adding to the actual claim being proven.
Is this basically what "defense in depth" means?
Yes, exactly — this module is a direct, hands-on, measured demonstration of that very common security phrase, which is often stated as received wisdom without anyone showing WHY it's true. Here, it's not received wisdom — it's a table of real, captured pass/fail results.
Could Scenario D still be bypassed by some third mechanism this course didn't build?
Almost certainly, in a real system — this module never claims Scenario D represents PERFECT, unbreakable security, only that it is demonstrably, measurably stronger than either single layer alone. Real production sandboxes are judged the same way: not as perfect, but as requiring an attacker to defeat an increasing number of independent, real mechanisms.
What's the actual takeaway for MY OWN future security work?
When evaluating (or designing) any single security control, ask precisely what it does and doesn't cover — the way this module explicitly separated "blocks process spawning" from "blocks file writes" rather than treating "sandboxing" as one vague, undifferentiated concept. Real gaps hide exactly in the space between two controls that each sound like they cover "the same thing" but actually don't.
