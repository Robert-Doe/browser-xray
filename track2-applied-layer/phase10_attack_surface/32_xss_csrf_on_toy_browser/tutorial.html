xss_csrf_on_toy_browser

Proves: a real XSS payload and a real CSRF attack both succeed against this course's own toy browser stack — until the specific defensive module (CSP, SameSite) already built in Phase 9 is actually wired in, at which point they fail, with no other change.

00Prerequisites

Module 30: csp_enforcement Module 29: cookies_samesite Module 20: dom_tree_builder

01The Big Analogy

A fire drill doesn't just describe what smoke does — it sets a real (controlled, contained) fire and watches whether the alarm actually triggers and the sprinklers actually engage. Anyone can assert "the sprinkler system works." A real drill proves it, on this specific building, with this specific fire, and it's the only way to know the answer for certain rather than trusting the building's blueprint. This module is that drill: two real, well-understood attacks, run against the specific toy building this course spent 31 modules constructing, checked against its actual, already-installed sprinklers — not a different building, not a hypothetical one.

02What Happens, Step by Step

  1. XSS: a comment containing a real <script> payload is inserted into a page via naive string concatenation — the actual, common root cause of real stored-XSS vulnerabilities.
  2. That page's HTML is fed through this course's OWN tokenizer and DOM builder (Modules 19–20) — proving the injected script is a real, structural <script> element in the parsed DOM, not just suspicious-looking text.
  3. With no CSP header, Module 30's own check_script() confirms that script would run. With a real script-src 'self' policy applied, the identical script is confirmed blocked.
  4. CSRF: a hidden, auto-submitting cross-site form targets a toy bank's transfer endpoint.
  5. Module 29's own real CookieJar decides whether the victim's session cookie is attached — SameSite=None attaches it (transfer succeeds); SameSite=Lax doesn't (transfer rejected).
