layout_box_model

Proves: layout is a genuine recursive geometry computation — every box's real x, y, width, and height derives mechanically from its parent's available space, its own CSS box-model properties, and its children's own computed geometry.

00Prerequisites

Module 22: style_computation

01The Big Analogy

A moving crew stacking boxes into a truck doesn't know in advance exactly where each box will sit — they know the truck's total width, and they place each box against the wall, filling it unless told a box needs to be narrower, then stack the next box directly on top of wherever the last one ended. No box's final position is decided ahead of time by a floor plan; it FALLS OUT of a simple, repeated rule applied one box at a time, top to bottom. Nobody computes the truck's total load height in advance either — it's just whatever height the stack of boxes actually adds up to, once they're all placed.

02What Happens, Step by Step

  1. An element's own margin and padding are read from its computed style (Module 22).
  2. If it has an explicit width, that's its content width. Otherwise, its content width fills whatever space its parent made available, minus its own margin and padding.
  3. Its children are laid out one at a time, each starting exactly where the previous one's box ended vertically — real block-flow stacking.
  4. If the element has no explicit height, its final height is simply the sum of everything its children ended up taking, plus its own padding.

Notice cursor_y only ever moves forward, by exactly the height of whatever was just placed. That one line IS block-flow stacking — there's no separate "positioning" step; position is a direct, mechanical consequence of processing children in order.

07Brain Exercise

Suppose `#container`'s CSS were changed to `width: 400px; box-sizing: border-box; padding: 10px;` (a real, common CSS property this module doesn't implement). Would you expect the container's TOTAL rendered width to still be 420px, or something else? Think about what `box-sizing: border-box` actually redefines before revealing the answer.
It would be exactly 400px, not 420px. `box-sizing: border-box` redefines what the `width` property MEANS: instead of describing content only (this module's implemented behavior, and CSS's default), it describes the TOTAL box including padding and border — so the content area actually SHRINKS to accommodate the padding within that same fixed 400px, rather than the total box growing past it. This is precisely why many real-world CSS resets (a common one: `* { box-sizing: border-box; }` applied globally) exist — content-box's behavior (where adding padding silently grows your total layout width) is widely considered less intuitive for most real page-building work, which is exactly why so many projects deliberately override CSS's own default. This module implements only the default; recognizing that `box-sizing` changes the width arithmetic itself, not just a cosmetic detail, is real, transferable CSS knowledge.

08There Are No Dumb Questions

Why does text contribute zero height in this module, when obviously text takes up visible space in a real browser?
Because correctly measuring text requires real font metrics (glyph widths, line heights, wrapping rules) — a substantial, separate subsystem real browsers implement with actual font rendering engines. This module's scope stops at block-level box geometry; text/inline layout is a deliberately named gap, not an oversight.
Is "auto width fills the container" true for EVERY element, or just some?
It's the default behavior specifically for BLOCK-level elements with no explicit width — which is what this module models throughout. Inline elements (like a `` or `` in real CSS) behave completely differently: they only take up as much width as their own content needs, which is exactly why this module doesn't attempt to model inline elements at all.
Why compute `cursor_y` by summing heights instead of, say, absolute-positioning each child directly?
Because that summing IS what block-flow layout actually is — there's no absolute coordinate system children are placed into independently; each one's position is defined relative to wherever the previous sibling ended. This is a faithful reproduction of the real algorithm's shape, not an implementation shortcut.
What would happen if a child element had a NEGATIVE margin?
This module's arithmetic would happily compute a wider content width and (if it affected `cursor_y`) potentially overlapping geometry — which matches real CSS: negative margins are a real, legal, sometimes deliberately-used technique to pull elements closer together or create overlap, not something CSS disallows.
