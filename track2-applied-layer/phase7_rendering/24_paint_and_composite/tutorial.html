paint_and_composite

Proves: paint and composite are genuinely separate pipeline stages — instrumented with real call counters showing that a compositor-only property change skips layout and paint entirely, while a layout-affecting change cannot.

00Prerequisites

Module 23: layout_box_model

01The Big Analogy

A theater has painted backdrops, already finished and hanging, and a movable rig that slides those backdrops left and right during a scene change. Repainting a backdrop is real, slow, skilled work. Sliding an already-painted backdrop three feet to the left is nearly instant — a stagehand just pulls a rope. If a director asks for the CONTENT of a backdrop to change, there's no shortcut: it has to be repainted. But if the director only wants it to be in a slightly different spot, repainting it from scratch would be a bizarre waste of a skilled painter's time when the rig was built for exactly that job.

02What Happens, Step by Step

  1. Layout (Module 23) produces real box geometry.
  2. Paint reads each box's visual style and records what color goes where, in that box's OWN local coordinates — a flat list of paint records, back-to-front.
  3. Composite walks the box tree once more, grouping paint records into layers — most share one base layer, but any element with transform (or will-change: transform) gets its OWN dedicated layer.
  4. Changing a layout property (like width) invalidates everything downstream: layout, then paint, then composite all have to run again.
  5. Changing transform on an element that ALREADY has its own layer only requires nudging that layer's offset — paint and layout are never touched.

04The Code, Explained

def change_compositor_only_property(self, element, dx, dy):
    for layer in self.layers:
        if any(r.box.element is element for r in layer.paint_records):
            layer.offset_x += dx
            layer.offset_y += dy
            self.composite_runs += 1
            return

Notice what this function never calls: _run_layout() or _run_paint(). It doesn't skip them by an optimization check — it structurally has no path that reaches them. That's the real architectural point: a dedicated layer's offset genuinely doesn't depend on anything layout or paint would recompute.

07Brain Exercise

Suppose a developer, wanting a "smooth" hover effect, animates an element's `top` and `left` CSS properties every frame instead of `transform: translate(...)`. Using this module's exact model, trace through what happens on EVERY SINGLE FRAME of that animation, and explain why this is a well-known, real performance complaint, before revealing the answer.
`top`/`left` are layout-affecting properties in this module's model (and in real browsers) — changing them moves where an element sits, which is exactly the kind of change `change_layout_affecting_property()` demonstrates. That means EVERY SINGLE FRAME of such an animation forces a full layout pass (recomputing geometry for that element and potentially everything affected by it), a full paint pass, and only then a composite pass — at whatever frame rate the animation runs (ideally 60 times per second). Compare that to a `transform`-based animation using this exact same model: every frame touches ONLY composite, which is dramatically cheaper work, repeated 60 times a second. This is precisely why real browser performance tooling (like Chrome DevTools' "Performance" panel) explicitly flags animations that trigger layout ("layout thrashing") as a common, real, fixable performance problem — and why "use transform, not top/left, for animations" is standard, well-founded advice rather than a superstition.

08There Are No Dumb Questions

Why doesn't EVERY element just get its own compositor layer, if layers are so much cheaper to update?
Because each layer has a real memory and management cost — giving every element its own layer would multiply GPU memory usage and layer-management overhead enormously, for elements that never actually need independent movement. Real browsers are deliberately selective about layer promotion for exactly this reason — it's a genuine tradeoff, not a free win to apply everywhere.
Is `background-color` ever a compositor-only property?
No — changing what color is painted is fundamentally a PAINT concern (the pixels themselves changed), never something composite alone could handle. This module's own `needs_own_layer()` check deliberately never looks at `background-color` for exactly this reason.
What would happen if `#mover` in the demo had never had `transform` set at all?
It would remain part of the shared base layer, and `change_compositor_only_property()` would find no dedicated layer for it and raise an error — matching real behavior: an element must already be "promoted" to its own layer (by having a triggering property present) before a transform-only update can skip layout and paint for it.
Does "paint" in this module correspond to anything real graphics hardware does?
Conceptually yes — real paint produces actual bitmap tiles via a rasterizer (e.g. Skia in Chromium), and real composite hands those already-rasterized tiles to the GPU to be positioned and blended. This module's `PaintRecord`/`Layer` objects are a structural stand-in for that real process, not a literal reimplementation of a rasterizer or GPU compositor.
