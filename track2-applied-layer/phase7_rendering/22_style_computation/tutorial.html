TRACK 2 · PHASE 7 · MODULE 22 · FIRST RENDERING-PIPELINE MODULE

style_computation

Proves: every DOM node gets one fully resolved computed style via a real, exactly-ordered cascade — !important beats specificity, specificity beats source order — before any layout or pixel exists.

00Prerequisites

Module 20: dom_tree_builder Module 21: css_parser_cssom

01The Big Analogy

A courtroom hears every applicable rule that could govern a case — general statutes, specific regulations, and any explicit overriding order a judge has issued — and resolves them in a strict priority order: an explicit override order wins no matter what, THEN the more specific regulation beats the general statute, and only if two rules are equally specific does whichever was enacted more recently win. No rule is thrown away just because a more specific one exists — they all get heard — but exactly one verdict comes out per question asked. Computing an element's style is exactly this: every matching CSS rule is heard, and the cascade is the strict, ordered process for reaching one final verdict per property.

02What Happens, Step by Step

  1. For a given DOM element, every rule in the CSSOM is checked: does any of its selectors match this element (including checking ancestors, for selectors like div p)?
  2. Every declaration from every matching rule is collected, tagged with whether it's !important, its selector's specificity, and its position in the original stylesheet.
  3. These candidates are sorted by that exact three-part priority: important-ness first, specificity second, source order third.
  4. For each property, the highest-priority candidate — the LAST one in that sorted order — is the final, computed value.

03What We Actually Captured

CSS:
.title { color: red; }
#header { color: blue; }
p { color: green !important; }
div p { font-weight: bold; }
.title { background: yellow; }


 computed style: {'color': 'blue', 'background': 'yellow'}
  -> color: blue, because #header (1 ID) outranks .title (1 class),
     regardless of which rule appeared first in the stylesheet


 (parent=div) computed style: {'font-weight': 'bold', 'color': 'green'}

 (parent=#document) computed style: {'color': 'green'}
  -> BOTH 
 elements get color: green, because !important overrides
     specificity entirely
  -> only the 
 INSIDE the div gets font-weight: bold, because
     'div p' genuinely does not match the top-level
Real, captured output. Three independent, correct cascade decisions from one small, deliberately tricky stylesheet.

04The Code, Explained

candidates.sort(key=lambda c: (c[0], c[1], c[2]))
style = {}
for important, spec, order, decl in candidates:
    style[decl.property] = decl.value

This is the entire cascade, in two lines. Sorting ascending by the real priority order, then simply overwriting each property as we go, means the LAST write for any property is automatically the correct winner — no separate "which one wins" comparison function to maintain or get subtly wrong.

05Limits / What You Cannot Do Yet

CAN'T DO YET

  • Match child (>), sibling (+, ~), attribute, or pseudo-class selectors — only type/class/ID/universal plus descendant combinators
  • Apply property INHERITANCE (e.g. color cascading down to children that set no color themselves) — a real, separate CSS mechanism, deliberately out of this module's scope
  • Turn any of this into actual pixels — that's Module 23

CAN DO NOW

  • Predict, correctly, which of several conflicting CSS rules wins for a given element and property
  • Explain precisely why !important beats even an ID selector, and why that's not a contradiction of "specificity matters"
  • Implement real CSS specificity comparison from first principles
