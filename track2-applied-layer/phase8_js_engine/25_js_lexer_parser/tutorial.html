01The Big Analogy

A sentence diagram in grammar school didn't tell you what a sentence MEANS — it told you its shape: which word is the subject, which phrase modifies which noun, how clauses nest inside each other. You could diagram a sentence perfectly and still never "execute" it — diagramming and understanding-in-order-to-act are two completely different operations, performed at two completely different times. An AST is a sentence diagram for code: a precise, complete map of structure and precedence, built entirely before anyone asks "okay, now what does this actually DO."

02What Happens, Step by Step

  1. The lexer turns raw source text into a flat stream of tokens — numbers, strings, identifiers, keywords, operators — skipping whitespace and comments entirely.
  2. The parser reads that token stream top-down: statements first (variable declarations, functions, if/while, returns), each of which eventually needs to parse an expression.
  3. Expressions are parsed via precedence climbing: a single loop that only continues consuming an operator if its precedence meets a minimum threshold — which is what makes 3 * 4 bind tighter than the + next to it, automatically.
  4. Function calls and member access (.property) chain onto whatever came before them, left to right.
  5. The result is a tree of plain data objects — a Program containing statements containing expressions — with no code anywhere that runs any of it.

03What We Actually Captured

2 + 3 * 4;  ->  BinaryExpr('+', 2, BinaryExpr('*', 3, 4))
2 * 3 + 4;  ->  BinaryExpr('+', BinaryExpr('*', 2, 3), 4)
a = b = 5;  ->  AssignmentExpr('=', a, AssignmentExpr('=', b, 5))
!x && y || z;  ->  BinaryExpr('||', BinaryExpr('&&', UnaryExpr('!', x), y), z)
Real, captured parser output. Same operators, different source order, genuinely different tree shapes — precedence made visible.

04The Code, Explained

def _parse_binary(self, min_precedence):
    left = self._parse_unary()
    while True:
        token = self._peek()
        if token.type != "OP" or token.value not in BINARY_PRECEDENCE:
            break
        precedence = BINARY_PRECEDENCE[token.value]
        if precedence < min_precedence:
            break
        operator = self._advance().value
        right = self._parse_binary(precedence + 1)
        left = BinaryExpr(operator, left, right)
    return left

One function, one small precedence table, and the entire expression grammar falls out of it. The precedence + 1 on the recursive call is the one detail doing the real work: it forces the right-hand side to bind only to operators STRICTLY tighter than the current one, which is exactly what makes 2 - 3 - 4 group as (2 - 3) - 4 and not the other way around.

07Brain Exercise

This parser builds the ENTIRE AST before Module 26 ever looks at any of it. Why is that separation — fully parse first, execute completely separately afterward — valuable even beyond keeping this course's modules clean? Think about what a real JS engine could check about your code before running a single line of it, before revealing the answer.
Because a complete AST lets an engine (or a tool) inspect and validate the ENTIRE program's structure before committing to run any of it — a syntax error in code that would only execute after ten minutes of runtime can still be caught immediately, before the program starts, precisely because parsing doesn't depend on execution reaching that point. This is also the foundation real engines build actual OPTIMIZATION on: V8's JIT compiler (which Module 27 gestures toward) can analyze a fully-formed AST/bytecode representation to decide how to optimize a function, well before that function has even been called once. None of that is possible if parsing and execution were interleaved — the complete-structure-first approach this module builds is a genuine prerequisite for both early error detection and later optimization, not just a clean way to organize a course.

08There Are No Dumb Questions

Why are keywords their own token TYPE instead of just identifiers that happen to say "if" or "while"?
Purely a clarity/convenience choice made at the lexer level — tagging them as `KEYWORD` lets the parser's statement dispatch check a token's TYPE rather than comparing strings against a keyword set everywhere it might matter. Either approach can work correctly; this one keeps the parser's own logic a little cleaner.
Why does this parser use Python `float` for every number, even something like `5` that looks like an integer?
Because that's genuinely accurate to real JavaScript — JS has exactly ONE numeric type (a 64-bit floating-point double) for every number, with no separate integer type at all. Using `float` throughout isn't a simplification; it's a faithful match to how JS itself represents numbers.
What happens if I write `2 + 3 * ` with nothing after the `*`?
The parser will eventually reach a token it can't turn into a primary expression (likely a semicolon or EOF) and raise a `SyntaxError` from `_parse_primary` — real, useful error behavior, since a genuinely incomplete expression like this isn't valid JS either.
Is precedence climbing the ONLY way to write an expression parser?
No — the "one function per precedence level" approach (a chain of `parse_or` → `parse_and` → `parse_equality` → ...) is equally real and common, and produces identical results. Precedence climbing is simply the more compact of two standard, correct techniques.
