00Prerequisites

01The Big Analogy

Imagine following a recipe by re-reading the entire cookbook page from scratch before every single step — checking the title, the ingredient list, the step number, and only THEN performing that one step — and doing this full re-read for every step, every time, even for a recipe you're making for the hundredth time today. It works. You'll get a correct dish. But you're paying the "which recipe, which step" overhead freshly, every single time, instead of ever remembering "oh, step 4 always just means crack two eggs" and skipping straight to doing it. A tree-walking interpreter is exactly this — correct, straightforward, and paying real, repeated overhead it never gets to amortize.

02What Happens, Step by Step

  1. To execute a statement, execute_statement checks the node's Python type via a chain of isinstance checks — every single time, even for the same node visited a hundred thousand times in a loop.
  2. Expressions work the same way through evaluate.
  3. Variables live in a real, linked-chain Environment — looking one up walks outward through parent scopes until it's found, exactly matching real JS scoping.
  4. A function call creates a brand-new Environment whose PARENT is the function's closure — the scope that existed when the function was originally defined, not where it's being called from.
  5. return is implemented by raising a Python exception that unwinds straight back out to the call boundary.

04The Code, Explained

def evaluate(node, env):
    if isinstance(node, NumericLiteral):
        return node.value
    if isinstance(node, Identifier):
        return env.get(node.name)
    ...
    if isinstance(node, BinaryExpr):
        return evaluate_binary(node, env)

Every single one of fib(24)'s roughly 150,000 recursive calls re-runs this ENTIRE chain of type checks, for every node it touches, from scratch. Nothing here remembers "last time we saw a BinaryExpr here, it meant subtraction" — that memory is exactly what a bytecode representation (Module 27) is built to provide instead.

07Brain Exercise

This interpreter's blocks don't create their own scope, meaning `let` inside an `if` behaves like `var` (visible outside the block) rather than real, block-scoped `let`. Write a short program in your head where this difference would produce genuinely WRONG behavior compared to real JS, before revealing one example.
Consider: `if (true) { let x = 5; } console.log(x);` — in real JS, this throws a `ReferenceError: x is not defined`, because `let`-declared `x` only exists inside the `if` block. In THIS module's interpreter, `x` would still be visible and equal to 5 after the block, because blocks share their parent's `Environment` rather than creating their own. This is exactly the kind of gap this module's `DECISIONS.md` flags explicitly rather than letting you discover it by surprise — a genuinely real difference from modern JS semantics, not a hidden bug pretending to be a feature. Fixing it would mean giving `BlockStatement` execution its own child `Environment` and letting variable lookup fail past that boundary once the block finishes — a real, natural extension this module deliberately left out to keep the scope model simple.

08There Are No Dumb Questions

Why use a Python exception for `return` instead of, say, a special sentinel return value threaded through every function?
Both are legitimate, real techniques. Exceptions let `return` unwind arbitrarily deeply nested control flow (a `return` inside three nested `if`s inside a `while`) in one motion, using Python's own stack-unwinding machinery, rather than needing every single statement-execution function to check "did a return already happen?" after every recursive call.
Does a real JS engine like V8 ever use a tree-walking interpreter at all?
Historically, early JS engines largely did work this way. Modern engines like V8 use a bytecode interpreter (Ignition) as a baseline tier specifically because of the exact cost this module measures, with a JIT compiler (TurboFan) further optimizing hot code beyond even that — Module 27 builds the bytecode step of that real, historical progression.
Why does `fib(10)` print as `55.0` instead of `55`?
Because every number in this interpreter is a Python `float`, matching real JS's own single numeric type exactly (see Module 25's `DECISIONS.md`) — `55.0` and `55` represent the identical numeric value; JS itself doesn't distinguish them either.
Could this interpreter run a REAL, unmodified JS program from the actual web?
Only if that program stayed entirely within this module's implemented subset (Module 25's scope: no object/array literals, arrow functions, `for` loops, etc.) — most real-world JS uses features well beyond what this course's engine implements, which is an intentional, stated scope boundary, not an oversight.
