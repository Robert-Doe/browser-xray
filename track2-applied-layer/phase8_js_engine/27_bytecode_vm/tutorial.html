01The Big Analogy

Remember Module 26's cook re-reading the whole cookbook before every step? Now imagine that same cook, before starting to actually cook, first transcribes the recipe onto a single strip of index cards, one short instruction per card, in order: "crack egg," "whisk," "add flour." Cooking now means flipping through a stack of cards — plain, terse, unambiguous instructions — one at a time. Nobody re-reads the whole cookbook anymore; the "which recipe, which step" question was answered ONCE, during the transcribing, and never needs asking again. That transcription step is the compiler. The stack of cards is the bytecode.

02What Happens, Step by Step

  1. The compiler walks the AST exactly once, per function, emitting a flat list of small instructions — LOAD_CONST, LOAD_VAR, BINARY_OP, JUMP_IF_FALSE, CALL, RETURN, and a few others.
  2. Control flow (if, while) becomes explicit jump instructions with computed target addresses — no more tree structure, just "go to instruction N."
  3. The VM runs a tight loop: read the instruction at the current program counter, advance the counter, act on a small value stack, repeat.
  4. Every one of fib(24)'s ~150,000 calls now reruns this same tight loop over a SHORT, ALREADY-COMPILED list of instructions — no AST, no isinstance chains, at all.

07Brain Exercise

This module's speedup (roughly 1.84x) is real but modest — nowhere near the difference between, say, interpreted Python and compiled C. Given that both Module 26 and Module 27 are themselves written in Python and run on the same Python interpreter, why would you expect the GAP between "tree-walking" and "bytecode" to be much LARGER in a real engine written in C++ (like V8) than what this module measured? Think about what's actually being compared in each case before revealing the answer.
Because in THIS module, both approaches pay an enormous, shared, FIXED overhead: every single operation — pushing to a stack, checking an opcode, calling a Python function — already goes through Python's own interpreter loop, its own object model, and its own dynamic dispatch machinery. That shared cost dominates both measurements roughly equally, which is exactly why the gap between them is modest — we're comparing two strategies implemented in the same relatively slow host environment. A real engine written in C++ has no such shared floor: its tree-walking version (if one existed) would pay real, uncushioned recursive function-call and dynamic-type-check costs on bare metal, while its bytecode version runs an extremely tight, often hand-optimized dispatch loop with none of that overhead — which is why the REAL difference between these two strategies, measured in a real engine's native implementation language, is dramatically larger than what this Python-on-Python comparison shows. This module's result is honest and real for what it measures; it deliberately doesn't claim to reproduce the absolute magnitude a native implementation would show.

08There Are No Dumb Questions

Why isn't this module's speedup bigger?
Because both implementations are themselves interpreted Python code — see the Brain Exercise above. The RELATIVE improvement (less dispatch overhead, no repeated tree traversal) is real and would hold in any implementation language; the ABSOLUTE size of that improvement depends heavily on how much overhead the host language itself already adds underneath both approaches.
Is "opcode" just a fancy word for "instruction"?
Essentially yes — "opcode" (operation code) specifically refers to the part of an instruction that identifies WHICH operation to perform (`LOAD_CONST`, `BINARY_OP`, etc.), as distinct from the instruction's argument/operand (the actual constant value, which operator). This module represents both together in one `Instr` object for simplicity.
Why does `CALL` need to know the argument count (`argc`) explicitly?
Because the VM's value stack is untyped and doesn't otherwise know how many of the values currently on top of it belong to this particular call's arguments versus something pushed earlier — encoding the count directly in the instruction is what lets `CALL` correctly pop exactly the right number of values, in the right order (reversed, since they were pushed left-to-right but popped last-in-first-out).
Does real V8 have exactly these instructions?
Not these exact names or this exact instruction set — V8's real Ignition bytecode has dozens of specialized instructions tuned for real JS semantics and performance. This module's instruction set is a small, real, but deliberately minimal one covering exactly what this course's JS subset (Module 25) needs.
