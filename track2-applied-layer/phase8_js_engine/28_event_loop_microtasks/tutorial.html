01The Big Analogy

A single bank teller serves one customer completely before calling the next — no interruptions, no parallel service, just one queue at a time, worked strictly in order. But this teller has TWO trays: an "urgent" tray and a regular line. The rule is absolute: after finishing with whoever's currently at the window, check the urgent tray and completely empty it — every single slip, including any NEW urgent slip someone drops in while the teller is still working through the tray — before calling the next person from the regular line. There's still only one teller, doing one thing at a time. The "urgent tray always fully empties first" rule is the entire trick — no actual parallelism required.

02What Happens, Step by Step

  1. The script's own top-level code runs immediately, synchronously — script start and script end both happen before the event loop does anything at all.
  2. Along the way, some callbacks are queued as MACROTASKS (setTimeout), others as MICROTASKS (Promise.then).
  3. Once the script's synchronous code finishes, the event loop fully drains the microtask queue — running every microtask, including any new ones queued by microtasks that just ran.
  4. Only then does the FIRST macrotask run — followed immediately by another full microtask drain, then the next macrotask, and so on.

04The Code, Explained

def _drain_microtasks(self):
    while self.microtasks:
        callback, label = self.microtasks.popleft()
        callback()  # might queue MORE microtasks -- the while loop will see them

That while self.microtasks: — re-checked every single iteration, not a fixed count taken up front — is the entire mechanism. It's what lets "promise 2" queue "promise 3" mid-drain and still have "promise 3" run before either setTimeout callback, exactly matching real JS.

07Brain Exercise

Suppose a microtask callback queued ANOTHER microtask, which queued ANOTHER, which queued another — forever, with no terminating condition. Using this module's exact `_drain_microtasks` loop, what would actually happen? Would any macrotask (like a `setTimeout`) EVER get to run? Think it through before revealing the answer.
No macrotask would ever run — the `while self.microtasks:` loop would spin forever, since a microtask that always queues another microtask means the queue is NEVER empty, and the draining rule is "keep going until it's empty," not "run for a while and then move on regardless." This is a real, well-known phenomenon in actual browsers too — an infinite microtask-queuing loop genuinely starves the event loop, freezing the page (no rendering, no `setTimeout` callbacks, no user input handling) because the browser's real event loop has this exact same "fully drain microtasks before anything else" rule. This is precisely why real JS style guides warn against unbounded recursive Promise chains with no escape condition — it's not a performance suggestion, it's a correctness hazard with the same mechanism this module just proved.

08There Are No Dumb Questions

Why does `setTimeout(fn, 0)` not run immediately, if the delay is zero?
Because "0ms delay" only means "as soon as possible, given macrotask scheduling rules" — it still has to wait for the current synchronous code to finish AND for the entire microtask queue to drain first, exactly as this module's captured output shows. Zero delay was never a promise of immediate execution.
Is this why JS doesn't need thread locks/mutexes for its own code?
Yes, precisely — since only one callback ever runs at a time, with no true parallel execution of JS code itself, there's no possibility of two pieces of JS simultaneously reading/writing the same variable in a genuinely racy way. (Real browsers DO have actual parallelism elsewhere — separate processes/threads for rendering, networking, etc. — but JS's own single-threaded execution model on the main thread is exactly why THIS specific class of bug doesn't apply to plain JS code the way it does in genuinely multi-threaded languages.)
What's the real-world difference between a microtask and a macrotask, beyond the draining rule?
Practically: microtasks (Promises, `queueMicrotask`) are meant for "finish this unit of asynchronous work as soon as possible," while macrotasks (`setTimeout`, I/O callbacks, UI events) represent genuinely separate, later "ticks" of the event loop — allowing the browser to do other things (like rendering a frame) between macrotasks, but never between microtasks in the same drain.
Could a page's rendering happen in between microtasks, the way it can between macrotasks?
No — real browsers specifically render between macrotasks (or between animation frames), never in the middle of a microtask drain, which is exactly why an unbounded microtask loop (this module's Brain Exercise) freezes the page's visuals entirely, not just its `setTimeout` callbacks.
